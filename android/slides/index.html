「Android教材」をホーム画面に追加する

アイコン1つから、通常教材・簡易版スライド・詳細版の深掘り講座を選べます。Safariのタブバー・アドレスバーがないアプリ表示で起動します。

  1. iPhoneのSafariでAndroidの共通入口を開きます。
  2. 共有メニューから「ホーム画面に追加」を選びます。
  3. 「Webアプリとして開く」が表示された場合はオンにして、「Android教材」として追加します。
  4. ホーム画面の「Android教材」アイコンから起動し、教材を選びます。動画は停止状態で開きます。

以前の「Android学習」「Android深掘り」アイコンは自動統合されません。記録がある場合は、このページの「学習記録の引き継ぎ・バックアップ」でファイルに保存してから、新しいアプリで読み込んでください。全画面のときは「全画面を終了」で記録の操作を表示できます。記録を確認するまで古いアイコンは残してください。閲覧には通信が必要です。

読み上げの声・使い方

「読み上げ」をオンにして再生すると、端末の日本語音声で説明を読みます。読み終わってから次の説明へ進むため、所要時間は声や速度によって変わります。

停止・再開では、現在の説明を先頭から読み直します。速度は再生速度の設定と連動します。声や速度を変えた場合も現在の説明を読み直します。画面を離れると停止します。音が出ない場合は端末の音量と日本語音声を確認してください。音声が利用できない場合は字幕で閲覧を続けられます。

録音ファイルは使いません。日本語音声は端末内のものを優先しますが、利用できる声や通信の有無はOS・ブラウザに依存します。読み上げのオン／オフと声の選択は、このブラウザに保存します。

      Androidには、いくつかの製品がある

      同じAndroidでも、なぜ動作が違う？

      1. AOSPはAndroidの基本となる公開ソースです。
      2. 端末メーカーがHAL・ドライバー・設定を組み込みます。
      3. SDKのAPIを通して、アプリが機能を利用します。
      4. スマートフォンやAAOSでは、製品の前提が異なります。

      AOSPにGoogleのサービス一式が含まれるとは限りません。OS版、targetSdk、ライブラリ版、製品で採用した構成を別々に記録します。AAOSとスマートフォン連携のAndroid Autoも別のものです。

      説明用の実例：製品構成の例

      1. 基盤：AOSP — 公開ソースがOSの土台になる
      2. 製品：HAL + 機器 — メーカーが製品の実装を組み込む
      3. 契約：SDK API — アプリは公開された窓口を使う
      4. 照合：OS × 製品 — 同じOS版でも採用機能は異なる

      要点：OSの版だけでなく、製品の構成を確かめる。

      確認問題：「Android 16なら、どの端末でも同じ機能が使える」は正しい？

      解答：OS版だけでは決まりません。ハードウェア、HAL、権限、製品設定、アプリ側の対象APIも確認します。

      アプリの下に、役割の層がある

      APIは成功。でも、機器は変わらない？

      1. アプリは公開APIへ要求を出します。
      2. Frameworkやシステムサービスが要求を扱います。
      3. HALは製品固有のハードウェア機能との境界です。
      4. ドライバーや実機の状態を経て、結果が観測されます。

      図は代表的な依存関係を簡略化しています。すべてのAPIが同じHALを通るわけではありません。故障の切り分けでは、どの層で要求と結果が途切れたかを探します。

      説明用の実例：機器制御を追う例

      1. 要求：setLevel(5) — アプリから公開APIへ要求する
      2. 受付：accepted — サービスが受け付けた段階
      3. 境界：HALへ委譲 — 製品固有の実装へ処理を渡す
      4. 観測：実測値を取得 — 呼び出し成功と機器反映は別

      要点：受付・実装・実機反映を、層ごとに切り分ける。

      確認問題：アプリのAPI呼び出しが戻れば、機器の反映も完了している？

      解答：必ずしも完了していません。APIの受付と、実機の反映・状態通知の時点を分けて確認します。

      アプリの起動と、処理する場所

      なぜ、通信待ちで画面まで固まる？

      1. システムが、必要なアプリプロセスの起動を判断します。
      2. Zygoteをもとに、アプリ用プロセスが生成されます。
      3. ARTの実行環境で、アプリのコードが動きます。
      4. メインスレッドが入力や画面更新などを順に処理します。

      ARTは最後に呼ぶ独立した処理段階ではなく、コードの実行を支える環境です。メインスレッドで長いI/Oを行うと、入力や描画の処理が待たされます。プロセスとスレッドを区別してください。

      説明用の実例：メインループの例

      1. 開始：起動要求 — 必要なアプリプロセスを準備
      2. 生成：Zygote → App — 実行用のプロセスが生まれる
      3. 実行：ART上のコード — ARTは最後の処理段階ではない
      4. 待ち：I/O待ち 500ms — この間、メインの入力・描画も待つ

      要点：メインスレッドを待たせると、入力と描画も待つ。

      確認問題：重い通信をメインスレッドで待つと、なぜ画面が固まる？

      解答：同じスレッドの入力・描画などが処理できなくなるためです。非同期にし、結果を適切なスレッドへ戻します。

      SLIDE 5 / 32

      別プロセスへ、要求が渡る

      別プロセスを呼ぶと、何を待つ？

      1. 呼び出し側がAIDLなどの契約に従って要求します。
      2. Binderを通して、別プロセスの境界を越えます。
      3. 受け手が権限や引数を検査し、要求を処理します。
      4. 戻り値と、後から届く通知を区別して受け取ります。

      同期呼び出しは相手の応答を待つため、呼び出すスレッドに注意します。onewayでも処理の成功や実機反映が保証されるわけではありません。サービス死亡や再接続も設計に含めます。

      説明用の実例：Binder通信の例

      1. 送信：setLevel(5) — 契約に従って要求を作る
      2. 転送：Binder → Service — プロセス境界を越える
      3. 検査：permission: OK — 受け手が権限と引数を検査する
      4. 応答：accepted ≠ applied — 受付の応答と実機反映は別に観測

      要点：同期の応答と、後から届く通知を分けて設計する。

      確認問題：onewayにすれば、相手の処理は必ず成功する？

      解答：いいえ。待ち方が変わるだけで、処理結果の保証とは別です。必要なら結果通知や状態の再取得を用意します。

      画面の入口と、戻る先を分ける

      「戻る」は、どの画面へ戻る？

      1. Intentが、行いたい操作や対象を表します。
      2. システムが条件に合う受け手を解決します。
      3. Activityが画面の入口となり、状態に応じて動きます。
      4. タスク内の履歴が、戻る操作の行き先に関係します。

      Activity、Service、BroadcastReceiver、ContentProviderにはそれぞれ役割があります。Serviceが自動的に別スレッドになることはありません。起動モードやフラグでタスクの挙動も変わります。

      説明用の実例：画面遷移の例

      1. 意図：詳細を開く — Intentで操作と対象を表す
      2. 解決：対象を選ぶ — システムが受け手を解決する
      3. 表示：詳細画面 B — Activityが画面の入口になる
      4. 履歴：B → Aへ戻る — 例：同じタスクの前の画面へ戻る

      要点：Activityの入口と、タスク内の履歴を区別する。

      確認問題：Serviceへ処理を移せば、重い処理は自動的に別スレッドになる？

      解答：なりません。実行するスレッドを別途設計する必要があります。Serviceは処理の役割と寿命に関するコンポーネントです。

      画面の状態と、保存の寿命

      画面が消えたら、アプリも終わる？

      1. 画面の作成時に、必要な初期化と復元を行います。
      2. 画面が見える状態へ進みます。
      3. 操作可能な前面の状態になります。
      4. 前面を離れる際に、処理や観測の継続条件を見直します。

      図は代表的な前面化と離脱です。構成変更やプロセス終了では経路が異なり、onDestroyが必ず呼ばれるとは限りません。ViewModelと永続保存の寿命も別です。バックグラウンド実行にはOSとtargetSdkの制限があります。

      説明用の実例：前面化と離脱の例

      1. 作成：onCreate — 初期化と状態の復元を行う
      2. 可視：onStart — 画面が見える状態へ進む
      3. 前面：onResume — ユーザーが操作できる状態
      4. 離脱：onPause / Stop — プロセス終了と同じではない

      要点：画面・プロセス・保存データは、それぞれ寿命が違う。

      確認問題：onDestroyでだけ保存すれば、プロセス終了後も必ず復元できる？

      解答：できません。コールバックが保証されない終了があります。必要な状態を適切な時点と保存先へ記録します。

      起動完了と、ユーザーの準備

      起動したのに、なぜデータを読めない？

      1. 起動するイメージの選択や検証を経て進みます。
      2. Kernelとinitが、OSの土台とサービスを立ち上げます。
      3. システムサービスやアプリの実行環境が準備されます。
      4. ユーザーの解錠状態により、利用できるデータが変わります。

      図は起動経路の一部です。Device Encrypted領域とCredential Encrypted領域では利用できる時点が異なります。BOOT_COMPLETEDを受けたことと、製品で必要な全機能の準備完了は同じではありません。

      説明用の実例：解錠前後の例

      1. 検証：Bootloader — 起動対象の選択・検証を経る
      2. 土台：Kernel / init — 必要なサービスを立ち上げる
      3. 起動：SystemServer — システム機能を準備する
      4. 解錠：CE領域が利用可 — ユーザー状態と保存領域を確認

      要点：起動完了と、ユーザー解錠後の利用可能性は別。

      確認問題：OSが起動したら、ユーザーの全データをすぐ読める？

      解答：解錠前に利用できないデータがあります。ユーザー状態と保存領域の条件を分けて扱います。

      画面OFFと、休止は同じではない

      画面OFFなら、通信も止まっている？

      1. 画面が消えても、処理や通信が続く場合があります。
      2. WakeLockやOSの制約、ハードウェア状態を確認します。
      3. 条件が整ったときに、サスペンドへ進める場合があります。
      4. 復帰後は接続や機能の状態をもう一度確かめます。

      画面、Androidの電源状態、Kernelのサスペンド、ホストOSや車両の状態は別の軸です。Dozeと物理サスペンドも同一ではありません。保持すべき処理には理由と解放条件が必要です。

      説明用の実例：休止できる条件の例

      1. 表示：画面はOFF — 画面が消えても処理は続く場合がある
      2. 制約：保持条件あり — WakeLockなどの保持条件を確認
      3. 休止：条件成立を確認 — 条件が整った場合だけ休止へ
      4. 復帰：接続を取り直す — 復帰後に接続と機能を再確認

      要点：画面OFF・Doze・サスペンドは、同じ状態ではない。

      確認問題：画面OFFを検出したら、通信も止まったと断定できる？

      解答：できません。画面と通信の状態は別です。対象のネットワークや処理の状態を観測します。

      一つのフレームが届くまで

      描画したフレームは、どこで待つ？

      1. アプリが表示内容を作ります。
      2. 描画結果がバッファとして受け渡されます。
      3. SurfaceFlingerがレイヤを合成します。
      4. 表示側との同期を経て、画面へ提示されます。

      図は描画側の簡略化した経路です。入力は機器からInputReader、InputDispatcherなどを通る別の経路です。フレーム時間の調査では、CPU、GPU、合成、表示待ちを分けます。

      説明用の実例：フレームの受渡し例

      1. 描画：Frame 042 — アプリがフレームを作る
      2. 受渡し：Buffer ready — バッファとして次の段階へ渡す
      3. 合成：Layers → 1 frame — 複数のレイヤを合成する
      4. 表示：Display present — 表示タイミングに合わせて提示する

      要点：アプリ・GPU・合成・表示待ちを分けて観測する。

      確認問題：描画が遅いとき、アプリの処理時間だけ見れば十分？

      解答：十分ではありません。GPUや合成、表示タイミングの待ちも含め、どの段階で遅れたかを追います。

      音が機器へ届くまで

      Focusはある。なのに、音が出ない？

      1. アプリが再生APIから音声データを渡します。
      2. 音声処理やミキシングを経ます。
      3. HALを介し、製品の音声経路へ進みます。
      4. DSPやアンプ、スピーカーなどへ届きます。

      音声データの経路を示しています。Audio FocusやMediaSessionなどの制御とは分けて考えます。Focusを得ても出力機器、音量、ゾーン、電源などの条件で聞こえない場合があります。

      説明用の実例：無音を切り分ける例

      1. 制御：Focus: GRANTED — これは再生制御の条件の一つ
      2. データ：PCM: あり — データが流れているかを確かめる
      3. 経路：Speaker route — 出力先と機器の経路を照合する
      4. 観測：Mute: ON — 例：ミュートが原因で聞こえない

      要点：Audio Focus取得は、音が聞こえる保証ではない。

      確認問題：Audio Focusを得たのに音が出ないのは、矛盾している？

      解答：矛盾しません。Focusは制御上の条件の一つです。出力経路・音量・ミュート・機器の状態を確認します。

      通信可能は、複数の条件で決まる

      権限があれば、サーバーにつながる？

      1. ケーブルや無線の接続状態を確かめます。
      2. アドレスと必要な経路があるかを確認します。
      3. 宛先の名前解決や検証の条件を確認します。
      4. 対象の通信先へ、アプリの条件で到達できるかを見ます。

      項目は別々の観測軸で、一列の状態遷移ではありません。インターネットの検証が成功しなくても、車内のローカル通信が使える場合があります。権限と通信の到達性も別です。

      説明用の実例：通信条件を分ける例

      1. リンク：Ethernet: UP — 物理接続があることを確認
      2. IP：192.0.2.10 — 説明用アドレス。設定と経路を確認
      3. 名前：DNS: 不成功 — リンクがあっても名前解決は別
      4. アプリ：通信: 未成功 — 権限だけでは到達性は保証されない

      要点：権限と、リンク・経路・到達性を混同しない。

      確認問題：INTERNET権限があれば、目的のサーバーへ必ず接続できる？

      解答：いいえ。権限は接続を許す条件であり、リンク・経路・名前解決・相手の状態なども必要です。

      症状から、証拠へ進む

      再起動で直った。それで原因は分かった？

      1. 固まり、終了、再起動など、現象を区別します。
      2. いつ・どのプロセスで起きたかを固定します。
      3. 例外、ANR、メモリ、システムの観測を集めます。
      4. 原因の候補を絞り、再現試験で確かめます。

      アプリの例外、ANR、メモリ不足による終了、システム全体の異常は別です。再起動で直ったことだけでは原因は分かりません。観測した事実と推測を分けて残します。

      説明用の実例：事実と仮説を分ける例

      2. 受付：accepted — 権限・引数の検査を通る
      3. 実装：HAL → Driver — 製品の実装を経由する
      4. 実測：observed = 3 — 例：まだ要求値には反映されていない

      要点：要求・受付・反映・観測を分けて記録する。

      確認問題：受付の応答と、機器の状態通知を別に持つ理由は？

      解答：受付後の反映遅延や失敗を表せるためです。要求した値と実測値を混同しないようにします。

      ADBは、三つの役割でつながる

      ADB接続ができれば、アプリも正常？

      1. PC側のクライアントがコマンドを受け取ります。
      2. PC側サーバーが接続を管理します。
      3. 端末上のadbdと通信します。
      4. 権限と接続条件に従って、対象の操作を行います。

      ADBの接続・認証状態と、Android内の機能状態は別です。userビルド、root、JDWP、アプリ権限の条件も区別します。複数端末ではシリアルを固定します。

      説明用の実例：接続と機能を分ける例

      1. 命令：adb client — PC側がコマンドを受け取る
      2. 管理：adb server — PC側で対象の接続を管理
      3. 端末：adbd: 接続済み — ここまでが接続に関する確認
      4. 機能：アプリを別途確認 — 接続だけではアプリ正常とはいえない

      要点：ADBの接続と、Android内の機能状態は別。

      確認問題：adb devicesに表示されれば、対象アプリの問題もない？

      解答：接続状態が分かっただけです。アプリやシステム機能の状態は別途確認します。

      SLIDE 30 / 32

      大量の記録を、発生時刻へ絞る

      採取した状態は、発生時の状態？

      1. 症状、操作、ビルド、ユーザー状態を残します。
      2. bugreportを採取し、構成を把握します。
      3. 発生と採取の時刻、再起動の前後をそろえます。
      4. 関連するログや状態をつなぎ、仮説を検証します。

      bugreportには採取時点の状態と保存されていたログが含まれます。発生時の全状態が保存されるとは限りません。個人情報などを含み得るため、製品での採取・共有条件にも従います。

      説明用の実例：発生と採取の照合例

      1. 発生：10:00 症状発生 — 操作・前提・ビルドを記録
      2. 採取：10:05 bugreport — 採取は発生の5分後という例
      3. 照合：5分の差がある — その間の復帰・再起動を確認
      4. 判断：保持範囲を限定 — 発生時の全状態が残るとは限らない

      要点：発生時刻・採取時刻・ログの保持範囲を照合する。

      確認問題：採取時点の状態を、そのまま発生時の状態だと扱ってよい？

      解答：同一とは限りません。時刻や再起動、ログの保持範囲を照合します。

      イメージと、配置と、起動

      Verified Bootは、暗号化のこと？

      1. 配布する成果物の単位を把握します。
      2. どの領域へ配置するかを整理します。
      3. マウントやVerified Bootなどの関係を確認します。
      4. スロット、更新の適用、復旧の条件と結び付けます。

      図は役割の対応を示すもので、単純な一方向の起動順ではありません。super内の動的パーティション、A/BやVirtual A/Bなどは端末構成で異なります。Verified Bootと暗号化も目的が別です。

      説明用の実例：イメージと配置の例

      1. 成果物：system image — 配布するイメージを把握する
      2. 配置：partition — 端末の構成に応じた領域へ配置
      3. 検証：Verified Boot — 整合性などを確認する役割
      4. 運用：更新 / 復旧 — スロットなど端末の条件と照合

      要点：配置・整合性の検証・暗号化は、別の目的。

      確認問題：Verified Bootと暗号化は、同じ機能？

      解答：異なります。起動時の整合性などの検証と、データを保護する暗号化は別の目的です。

      次は、実際の証拠で説明する

      その説明に、証拠は付いている？

      1. 説明したい現象と、前提をそろえます。
      2. 責任を持つ層と、要求が通る境界をたどります。
      3. 要求と結果を分け、ログや実測で確認します。
      4. 確認できた範囲と、残る条件を言葉にします。

      これで30章の中心となる見方を一巡しました。元のAndroid教材には、詳しい説明、コード、図、実習、確認問題があります。関心のある章へ戻り、手元の環境で確かめてください。

      説明用の実例：自分の言葉で説明する

      1. 問い：何が起きた？ — 現象と前提を一つにそろえる
      2. 責任：どの境界？ — 責任を持つ層と経路をたどる
      3. 証拠：何を観測した？ — 要求と実際の状態を照合する
      4. 説明：どこまで分かった？ — 確認できた範囲と次の問いを残す

      要点：分かった範囲と残る条件を、根拠と一緒に伝える。

      確認問題：分からない症状に出会ったとき、最初に残すと役立つ情報は？

      解答：何をしたか、いつ起きたか、対象の端末・ビルド・プロセス、期待した状態と実際の状態です。
