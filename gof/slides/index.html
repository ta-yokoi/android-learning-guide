      Bridge と Adapter

      1. Bridgeは通知の種類と送信経路など、独立して増える二つの変化軸を初めから分けます。

      1. Decoratorは同じ契約で包み、ログや変換などの責務を組み合わせます。順序も結果の一部になります。
      2. Proxyは実体へのアクセスを制御します。文書の遅延読込、権限検査、遠隔の代理などが候補です。
      3. ログを変換の外へ置くか内へ置くかで、記録する文字列が変わります。順序や例外の通り方も契約に含めます。
      4. 同じ契約で実体を保持する構造だけでは分類できません。責務を増やしたいのか、アクセスの条件を管理したいのかを先に述べます。

      同じ構造が異なる意図を持つ場合があります。実装の名前だけで判断しません。

      確認問題：重い文書を最初のreadまで生成しないラッパーは？

      解答・理由：遅延Proxyが候補です。ラッパーという構造だけでDecoratorとは決めません。

      GOF / SCENE 75

      State と Strategy

      1. Stateは未払い、支払い済み、発送済みのように、状態ごとの操作と許可された遷移を表します。
      2. Strategyは会員料金と通常料金のように、同じ目的のアルゴリズムを交換します。選択は利用側や組立側が担当します。
      3. Stateで操作の結果が変わるのは、現在の状態と遷移に意味があるためです。単なる手段の選択とは違います。
      4. Strategyも実行時に替えられますが、それだけでStateになるわけではありません。状態のライフサイクルをモデル化するのか、手段の違いを分離するのかで判断します。

      Template Methodは継承で手順の一部を変え、Strategyは合成で手段を交換するという比較も重要です。

      確認問題：会員の割引方式を組立側が渡すなら、注文の状態遷移か？

      解答・理由：その例はStrategyです。未払いから支払い済みへの遷移ならStateを検討します。

      注文通知 1｜一通から、送信経路の追加へ

      1. 最初の要求は注文確定後にメールを一通送ることです。直接関数を呼ぶだけで十分なら、抽象化を急ぎません。
      2. 次に顧客ごとにメールかSMSを選ぶ要求が増えました。注文処理が全経路のAPIを知ることが、新しい変更の痛みです。
      3. 送信の契約を用意し、外部SMSの契約差はAdapterで吸収する案があります。選んだ送信手段へ委譲する部分はStrategyの観点でも考えられます。
      4. 組立側が顧客条件で経路を選びます。継承で生成する要件がないなら、Factory Methodを増やすより注入が単純かもしれません。

      候補は要件から選びます。送信処理はこのページでは実行せず、設計の変更を説明しています。

      確認問題：SMS追加で、必ずFactory Methodを使うべき？

      解答・理由：必須ではありません。既存契約の変換はAdapter、送信手段の選択は注入やStrategyが候補です。生成の差替えが必要かを別に判断します。

      GOF / SCENE 77

      注文通知 2｜監査とログを、同じ責務にしない

      1. 注文確定を契機に、顧客通知とは独立した監査処理も動かしたいという要求が増えます。
      2. 独立した購読先を増減するならObserverが候補です。固定の二箇所へ呼ぶだけなら、明示した関数呼出しも比較します。
      3. 一つの送信へログを重ねる責務はDecoratorで分けられます。独立したイベント購読と、同じ送信の前後処理は異なる境界です。
      4. 購読解除の時点、例外で後続を止めるか、ログに機密情報を残さないかを決めます。通知の図だけで配送保証が得られるわけではありません。

      ObserverとDecoratorは併用できます。図で分かれた購読先と、入れ子のラッパーを取り違えないでください。

      確認問題：監査の失敗で顧客通知まで止めるかは、Observerが自動的に決める？

      解答・理由：決めません。例外方針、順序、再試行と必要な保証をアプリ側で設計します。

      注文通知 3｜再試行と注文状態を分ける

      1. 送信を後から実行したい場合、送信要求をCommandとして保持する案があります。要求の内容と実行する役割を分けます。
      2. 再試行すると二重送信の可能性があります。永続キュー、要求の識別子、冪等性、成功の記録はCommandだけでは得られません。
      3. 未払いでは発送できないという規則は、注文のStateで表す候補です。通知の送信待ちと注文の支払い状態は、同じ軸にまとめない方がよい場合があります。
      4. 状態遷移とイベントの保存をどう整合させるかは追加の設計です。小規模なら分岐や直接呼出しを残し、要件と失敗時の根拠で採否を決めます。

      唯一の正解はありません。想定する失敗、必要な保証、運用できる複雑さを説明した設計案を作ってください。

      確認問題：Commandにして再試行すれば、重複なく一度だけ届く？

      解答・理由：保証されません。配送と実行の成功は別です。識別子、永続化、冪等性や整合性の方針が必要です。
