CHAPTER 01

Androidの全体像と製品の種類

この章で分かることAndroid、AOSP、AAOS、Android Autoを区別し、学ぶ対象を説明できる。
前提知識一般的なOSとアプリの違い。

Androidは、アプリを実行するOSだけでなく、アプリ向けAPI、実行環境、ハードウェアへの接続口を含むソフトウェア基盤です。AOSPはその公開ソースコードです。「AOSPを入れる」だけで、すべての市販Android端末と同じアプリやサービスが揃うわけではありません。

名称位置づけ今回の読み方
AOSP公開され、製品向けに変更できるAndroidのソースコード共通の仕組みを学ぶ基盤
AAOS車載向けに構成・拡張されたAndroid OSCar Service等の追加機能と製品統合が必要
Android Autoスマートフォン側の体験を対応する車載画面で利用する仕組み車載器で動くAndroid OSそのものとは別。AAOSと共存も可能
GMSGoogleがライセンス提供するアプリ・サービス群AOSPとは別。製品への組込みと利用条件を確認
Google Play servicesGMSに関係する共通機能をアプリへ提供する部品GMS全体の別名ではない。AOSP単体で提供されるとは扱わない
GASOEMがライセンスして組み込む車載向けGoogleアプリ・サービス群AAOS採用とGAS採用を同じ判断にしない

本資料の主対象はAndroid 16（API level 36）です。AAOSには共通のAndroid基盤があり、その上で車載電源・音声・ユーザー等の機能が加わります。一般Androidの説明を車載製品へ適用するときは、有効な機能・権限・OEM設定を確認します。

共通例｜音楽アプリ

同じ音楽アプリでも、Googleの配信サービスへの依存、車載画面への対応、バックグラウンド再生の権限は別問題です。「Android 16で動く」だけでは製品で使えるかを判断できません。

想定製品：Qualcomm SoC＋サブマイコン、QNXホスト上のLinux VMとAndroid VM。ナビの主要機能はLinux側、Androidは主にアプリ用途です。本書はAndroid内部を中心に扱い、VM間やLinuxとの責務設計は保留します。

OS・SDK・ライブラリの版を分ける

対象何を決めるか記録例

CHAPTER 02

レイヤとコンポーネントの地図

この章で分かること役割の階層と、実際の実行場所を分けて考えられる。
前提知識第1章。

レイヤは「何を担当するか」という整理です。プロセスは「どこで実行するか」という整理です。Frameworkという一つのプロセスがあるわけではなく、アプリ内のAPI実装とOS側サービスが協調します。

レイヤ役割と主な部品実行場所／連携先
アプリActivity、Service、画面、アプリ固有データ通常はアプリのプロセス。Framework APIを利用
Framework APIPowerManager、AudioManager等の窓口呼び出し側アプリにもコードが存在。Binder等でOS側へ依頼
システムサービスアプリ管理、電源管理、Window管理等多くはsystem_server。すべてがここに集約されるわけではない
ART／NativeライブラリDEX実行・GC／C・C++等の処理アプリや一部システムプロセス内
NativeサービスSurfaceFlinger、audioserverなど独立プロセス等。Binderで要求を受ける
HAL機器ごとの実装差を吸収するインターフェースサービスプロセス等。具体的な構成はHALとBSPによる
Linuxカーネル／ドライバプロセス実行、メモリ、デバイス、休止Androidゲスト内のカーネル。ホストQNXとは別

AndroidもLinuxカーネルのプロセス・メモリ管理を使いますが、ユーザー空間は一般的なLinuxディストリビューションと異なります。Android init、Bionic、Binder、ART、Frameworkが重要です。通常のLinux向けバイナリやsystemd設定を、そのまま使えるとは考えません。

共通例｜音楽アプリ

音量変更は主に制御の流れ、再生する大量の音声データはデータの流れです。どちらも「アプリから音が出る」処理ですが、同じ経路・頻度で運ばれるとは限りません。

発展：HALは「ドライバの別名」ではない

HALは上位と機器実装を結ぶ契約です。ドライバはカーネル側の機器操作を担当します。仮想化製品ではHALから先が仮想デバイスや外部サービスにつながる場合があります。HAL全体で共通するREADY／STOPPEDという標準状態機械はありません。

機器操作の窓口と、受付・反映・観測・物理確認の違いは、第27章で具体例から学びます。

理解を確かめる

Q1. FrameworkのAPI呼び出しは、すべてアプリ内だけで完了しますか？

解答・解説を読む

いいえ。アプリ内で完了するものも、Binderを通して別プロセスのシステムサービスへ依頼するものもあります。

Q2. HALのプロセスが存在すれば、その機能は利用可能ですか？

解答・解説を読む

存在だけでは不十分です。接続、機器初期化、要求への応答など、機能固有の準備を確認します。

CHAPTER 03

プロセス・スレッド・ART・Zygote

この章で分かることアプリが実行される単位、生成方法、UIが固まる理由を説明できる。
前提知識第2章。

プロセスはプログラムのアドレス空間を持ち、スレッドはその中で処理を進めます。通常、アプリは固有のUIDとプロセスで分離されます。別プロセスの変数を、そのまま読むことはできません。UIDは権限・分離のための識別子で、PIDは実行中のプロセスの識別子です。

部品役割混同しないもの
メインスレッドアプリのUIや多くのコールバックを処理アプリに唯一のスレッド、という意味ではない
ワーカースレッドI/Oや時間のかかる処理を分離プロセスを存続させる保証ではない
ARTDEX形式のコード実行、GC、コンパイル等を担当すべてのNativeプロセスがART上で動くわけではない
Zygote共通の実行環境を準備し、アプリ等の生成元になるNativeデーモンを含む全プロセスの親、とは言わない
system_server多くの重要なJava系システムサービスを実行アプリのServiceをここで実行するわけではない

Kotlin／Javaで書いたコードは通常DEXとしてARTで動きます。Nativeライブラリは機械語として動き、JNIは両者を同一プロセス内でつなぐ窓口です。JNIを使ったからプロセス間通信になるわけではありません。

共通例｜音楽アプリ

曲一覧を表示するとき、メインスレッドで大量のファイルを読むと、タッチへの応答も遅れます。処理を非同期化しても、OSにプロセスの必要性を伝える仕組みや、キャンセル・保存は別途必要です。

発展：GCとメモリ設計

使われなくなった管理対象オブジェクトはGCが回収します。ただし参照を保持し続ければ回収できず、NativeメモリやOSリソースも別管理です。画面を破棄した後もActivityを参照し続ける構造は、車載器の長時間稼働で問題になります。

理解を深める追補

メインスレッドのイベント処理

Looperはスレッドでイベントを処理するループ、MessageQueueは処理待ちのキュー、Handlerはそのキューへ処理を渡す窓口です。Handlerを生成しても専用スレッドは作られません。UIスレッドで長いI/OやBinder待ちを行うと、次の入力や描画も待たされます。

Kotlin
// Application Contextを保持する等、呼び出し元の寿命にも注意する。
val mainHandler = android.os.Handler(android.os.Looper.getMainLooper())
mainHandler.post {
    // メインスレッドで短い処理をする。ここでファイル読込を始めない。
}

Executorはスレッド上の仕事を管理し、コルーチンはスコープとキャンセルを持つ非同期処理を表します。どちらもプロセスの生存、電源保持、ネットワーク許可を自動で保証しません。第18章で、非同期処理の寿命を画面・ViewModelと結びます。

理解を確かめる

Q1. Serviceを作ると専用スレッドが自動生成されますか？

解答・解説を読む

通常は生成されません。Serviceのコールバックも既定ではプロセスのメインスレッド上で実行されます。

Q2. JNIとBinderの違いは何ですか？

解答・解説を読む

JNIは管理対象コードとNativeコードを結ぶ仕組み、Binderは主にプロセス間の呼び出しを行う仕組みです。

CHAPTER 04

Binder・AIDLとシステムサービス

この章で分かること別プロセスへの依頼と、要求・受理・完了の違いを説明できる。
前提知識第2・3章。

Binderは、異なるプロセス間でメソッド呼び出しのように要求を送るAndroidの仕組みです。呼び出し側はProxy、受け側はStub等の生成コードを介して通信します。AIDLは、その通信で使うメソッドやデータ型を定義する言語です。

概念意味設計への影響
サービス取得公開されたサービスの窓口を得る取得成功だけで機器の準備完了を断定しない
同期呼び出し呼び出し元が戻りを待つUIスレッドで相手の長時間処理を待たない
oneway等の非同期呼び出し通常の同期応答を待たず依頼する受理・業務処理完了を同一視しない
コールバック結果や変化を相手から通知する通知スレッド、順序、再登録、初期値取得を定義
Binder death接続先プロセスの消失を検知する仕組み接続無効化→再取得→現在状態の再確認が必要
Stable AIDL独立更新される境界等の互換性を管理する仕組み普通のAIDL定義を書くだけで互換性管理が完成するわけではない
共通例｜音楽アプリ

音量変更のAPIが返った時点と、実際の出力が新しい音量に変わった時点には差があるかもしれません。基本設計では、APIの戻り値が「受付」「設定反映」「物理完了」のどれを表すかを契約ごとに確認します。

発展：ロックとコールバックの競合

別プロセスへの呼び出し中にロックを保持すると、相手からのコールバックや他の処理と待ち合う可能性があります。非同期化だけで解消するとは限りません。長時間処理、期限、キャンセル、要求IDを設計します。

理解を深める追補

ソースを読む順序と、要求の寿命

段階見るもの記録すること
API窓口Managerのメソッドと注釈公開範囲、権限、同期か、戻り値の意味
通信契約AIDL、生成Stub／Proxy引数、oneway、結果・例外、呼び出し元
サービス実装権限チェック、ロック、実処理実行スレッド、待ち、完了の根拠

接続には「準備中・接続済み・再接続中」等の製品状態を定義できますが、これらをBinder全体の標準定数として紹介しません。第20章でAIDLと切断処理の具体例を読みます。

理解を確かめる

Q1. AIDLを書けば、そのメソッドは常に別プロセスで動きますか？

解答・解説を読む

常にではありません。サービスの配置と取得先によります。インターフェース定義と実行場所は別です。

Q2. 状態変化通知を登録しただけで現在値を把握できますか？

解答・解説を読む

通知契約によります。初期通知の有無を確認し、必要なら登録と現在値取得の競合も設計します。

この章で分かること四大コンポーネントとApplication、Context、Intentの役割を使い分けられる。

この章で分かること起動完了の段階と、データが利用できる条件を説明できる。
前提知識第3・5・6章。

電源が供給されること、Androidが起動すること、ホームが表示されること、アプリが使えることは別の段階です。VM構成では、Androidゲストの起動開始をどこで観測するかも定義します。

OS内部の起動段階

内部フェーズ役割
PHASE_WAIT_FOR_DEFAULT_DISPLAY = 100既定ディスプレイの準備を待つ段階

// 構造例。Repository実装、ViewModelのFactory／DIは別途必要。
data class UiState(
    val loading: Boolean = false,
    val title: String = "",
    val error: String? = null
)
interface TitleRepository { suspend fun loadTitle(): String }

class LearningViewModel(private val repo: TitleRepository)
    : androidx.lifecycle.ViewModel() {
    private val mutable = kotlinx.coroutines.flow.MutableStateFlow(UiState())
    val state = mutable.asStateFlow()
    private var request: kotlinx.coroutines.Job? = null

    fun refresh() {
        request?.cancel()
        request = viewModelScope.launch {
            mutable.value = UiState(loading = true)
            try {
                mutable.value = UiState(title = repo.loadTitle())
            } catch (e: kotlinx.coroutines.CancellationException) {
                throw e // キャンセルを通常のエラーへ変換しない
            } catch (e: java.io.IOException) {
                mutable.value = UiState(error = "読込に失敗しました")
            }
        }
    }
}

suspend fun fetchText(endpoint: java.net.URL): String =

            as javax.net.ssl.HttpsURLConnection

            connection.readTimeout = 5_000

        } finally {

Ethernetの仕組みと車載ネットワーク

この章で分かること構成・状態・IP設定・Network選択を分け、接続から通信成功までを説明できる。
前提知識第2・4・8・11・14章。IPアドレス・サブネットの基本。

イーサネットは通信を運ぶ仕組みですが、「ケーブルが刺さった」と「アプリが目的の相手と通信できる」は同じ状態ではありません。この章はAndroid 16を対象にした理解の枠組みを示し、共通の仕組み、AAOSの管理機能、VM製品で決める条件を区別します。

1. 最初に覚える通信の層

対象役割次の層が使えるとは限らない理由
MAC／PHY・リンクフレームの送受信と物理・リンク条件リンクUPでもIP設定や相手のサービスが未準備の場合がある
IP設定アドレス、プレフィックス、経路等を用意IPアドレスがあっても目的先の経路がない場合がある
TCP／UDP等アプリが使うデータ転送パケット到達と、サーバーのポート・プロトコル成功は別
DNS等の名前解決ホスト名から宛先アドレスを得るリンクとIPが正常でも名前解決だけ失敗する場合がある
アプリの通信TLS、認証、HTTP、業務プロトコル等サーバー到達後にも認証・データ・業務エラーがあり得る

IPv4では同一リンクの相手や次ホップの解決にARP、IPv6では近隣探索（ND）等が関わります。通信先が同じサブネットなら通常の直接経路で届く場合があり、すべての通信にデフォルトゲートウェイが必須ではありません。L2／IP等の詳細は標準的なネットワーク知識ですが、AndroidではさらにNetwork単位の選択とアクセス条件を考えます。

2. Android内部の構成

部品主な役割利用対象・注意
ConnectivityManagerアプリ向けのNetwork・通知・経路選択API一般アプリも利用。APIごとの権限を確認
EthernetManagerEthernetの状態・設定・IF管理に関する窓口メソッドごとに公開範囲・権限が異なる。一般アプリで固定IPを自由に設定できるとはしない
EthernetService系・EthernetTrackerIFの追跡、リンクや管理設定の反映等内部実装の代表的名称。物理ポート名とIF名は一対一とは限らない
EthernetNetworkFactory系Ethernetの提供・要求やIP構成の調停等内部実装。現在の参考ソースと製品のAndroid 16版を区別
IpClient／DhcpClientIP層のプロビジョニング・維持／DHCP処理DHCPがすべてのIPv6構成を決めるわけではない
NetworkAgent／ConnectivityService提供するNetworkの情報と要求・既定経路等の調停物理的にリンクUPでも、アプリへ公開できるとは限らない
NetworkMonitor接続性の検証等公衆インターネットの検証と車内の目的先到達を分ける
netd／DNS Resolver低位ネットワーク設定を支える処理／名前解決現在のResolverはモジュール化され、単純にnetdだけの役割としない
カーネル・ドライバIF、アドレス、経路、隣接情報、パケット処理実際の機器や仮想NICの対応はBSP・基盤に依存
この章の内部クラス名・役割は公式解説とAOSP mainの参考ソースで確認しています。Android 16製品タグでの完全な照合・実機観測は未実施です。クラスの場所、分割、通知順序、機能フラグを本製品の実装契約として固定する前に確認してください。Ethernetの全経路へ共通の「Ethernet HAL」が必須である、とは説明しません。

3. リンク検出から通信可能まで

段階観測する事実まだ保証できないこと
IFが存在eth0等のインターフェースを認識有効化済み、物理リンク、IP設定
管理上有効IFを使う設定・権限・ポリシーがあるcarrierや相手の準備
リンク条件が成立物理／仮想リンクの通知がUP側アドレス・経路・DNS・業務通信
IP構成を取得／設定アドレス・プレフィックス・経路等目的先への適切なNetwork選択
Networkをアプリが利用対象にできる要求に一致したNetworkと情報を取得公衆インターネット、車内サーバーの業務成功
通信が成功選択したNetworkで必要な操作に成功今後も同じ接続が継続すること

NetworkCallbackのonAvailableは、フレームワークがNetworkを利用対象として通知する段階です。ケーブルの挿入直後に返る物理リンク通知と混同せず、続くonCapabilitiesChanged・onLinkPropertiesChangedの情報で判定を更新します。

4. DHCP・固定IP・IPv6を分ける

方式・設定何を確認するかよくある誤判定
DHCPv4サーバー応答、割当、リースと更新、経路・DNSDHCP成功をアプリの全通信成功とする
静的IPv4重複しないアドレス、prefix、必要な経路・DNSアドレスだけを設定して宛先経路を確認しない
IPv6リンクローカル、RA、SLAACやDHCPv6等、アドレスの状態IPv4のDHCPと同じ手順が必須とする
デフォルト経路他の具体的経路で届かない宛先への行先車内通信に不要でも、常に外向きゲートウェイを追加
DNS選択したNetworkのResolver設定と名前解決別Networkで名前を解決してからEthernetで接続する
VLAN・MTU論理分割とパケットサイズ、仮想基盤の対応VLAN IF名を見ただけで物理分離・アクセス許可を断定

AAOSではconfig_ethernet_interfacesのresource overlayや、権限を持つ管理アプリからの構成更新等が用意されています。overlayの値・数値定数・IF名・UID制限は製品で確認し、公式サンプルのIP値をそのまま製品へ移植しません。設定の受付完了と、実際のIP再構成・通信復旧の完了は分けます。

5. 複数ネットワークと車内通信

観点意味基本設計で決めること
既定Network通常の未指定の通信で用いるNetwork等アプリ・UID、VPN、ポリシーの影響を確認
INTERNET capability公衆インターネット向け能力の宣言車内のみのNetworkへ無条件に付けない
VALIDATED capabilityOSの検証でインターネット到達性を確認した状態車内の目的先に対する利用可能条件とは分ける
Restricted network利用するアプリ等が制限されたNetwork一般アプリが通知・接続できるとは限らない
Network指定の接続対象NetworkのDNS・Socket等を使う目的と期限、接続喪失時の再取得
プロセス全体のbindそのプロセスの未指定通信等へ影響一つの通信だけの変更と同一視しない
EthernetがリンクUPでVALIDATED=falseでも、車内のサーバーとは通信できる場合があります。逆にVALIDATED=trueでも、対象ポート、認証、車内サービスへのアクセスまで保証しません。Ethernetが複数ある場合も、IF名だけで選ばず、対象Networkとアクセス契約を照合します。

// start/stopと通知をメインスレッドにそろえる学習用の観測例。
class EthernetObserver(context: Context) {
    private val cm = requireNotNull(context.applicationContext
        .getSystemService(ConnectivityManager::class.java))
    private val handler = Handler(Looper.getMainLooper())
    private data class Snapshot(
        var capabilities: NetworkCapabilities? = null,
        var properties: LinkProperties? = null
    )
    private val states = mutableMapOf<Network, Snapshot>()
    private var registered: ConnectivityManager.NetworkCallback? = null
    private var generation = 0L

    fun start() {
        check(Looper.myLooper() == Looper.getMainLooper())
        if (registered != null) return
        val mine = ++generation
        val request = NetworkRequest.Builder()
            .addTransportType(NetworkCapabilities.TRANSPORT_ETHERNET)
            .removeCapability(NetworkCapabilities.NET_CAPABILITY_INTERNET)
            .build()
        val callback = object : ConnectivityManager.NetworkCallback() {
            override fun onAvailable(network: Network) {
                if (generation != mine) return
                states[network] = Snapshot()
                Log.i("EthLearning", "gen=$mine network=$network available")
                // ここで同期APIを再照会せず、次の通知の引数を利用する。
            }
            override fun onCapabilitiesChanged(
                network: Network, capabilities: NetworkCapabilities
            ) {
                if (generation != mine) return
                val state = states[network] ?: return
                state.capabilities = NetworkCapabilities(capabilities)
                report(network, state)
            }
            override fun onLinkPropertiesChanged(
                network: Network, properties: LinkProperties
            ) {
                if (generation != mine) return
                val state = states[network] ?: return
                state.properties = properties // 通知引数を変更せず保持する
                report(network, state)
            }
            override fun onLost(network: Network) {
                if (generation != mine) return
                states.remove(network)
                Log.i("EthLearning", "gen=$mine network=$network lost")
                // 対象Networkの通信結果・READY・古いSocketを無効化する。
            }
        }
        cm.registerNetworkCallback(request, callback, handler)
        registered = callback
    }
    private fun report(network: Network, state: Snapshot) {
        val caps = state.capabilities ?: return
        val lp = state.properties ?: return
        val internet = caps.hasCapability(
            NetworkCapabilities.NET_CAPABILITY_INTERNET)
        val validated = caps.hasCapability(
            NetworkCapabilities.NET_CAPABILITY_VALIDATED)
        Log.i("EthLearning", "network=$network iface=${lp.interfaceName} " +
            "addresses=${lp.linkAddresses} routes=${lp.routes} " +
            "dns=${lp.dnsServers} internet=$internet validated=$validated")
        // 情報がそろっても、目的の通信成功まで保証するものではない。
    }
    fun stop() {
        check(Looper.myLooper() == Looper.getMainLooper())
        generation++ // 既にキューにある旧通知も無効化する。
        registered?.let { cm.unregisterNetworkCallback(it) }
        registered = null
        states.clear()
    }
}

画面単位ならonStart等でstartし、対応するonStop等でstopする設計例があります。画面OFF中も監視する必要があるなら、適切なService等へ寿命を移します。どこからでも登録を増やさず、停止・再登録・権限エラーの処理をアプリ全体で調停します。ログにネットワーク情報を記録する範囲は、製品の診断方針で決めます。

このRequestはINTERNETを必須にしていませんが、他の既定capabilityやアクセス制限は残ります。すべてのrestricted Ethernetを一般アプリから列挙できるコードではありません。監視条件と、OEM管理アプリの権限は別に確認します。onLostも「物理ケーブルが抜けた」だけでなく、Networkがその監視条件を満たさなくなった場合に発生し得ます。

// 製品の判定設計例。Android標準enum・APIではない。
data class EthernetConditions(
    val currentNetworkUsable: Boolean,
    val targetRouteReady: Boolean,
    val targetOperationSucceeded: Boolean,
    val internetValidated: Boolean
)
fun localEthernetReady(c: EthernetConditions): Boolean =
    c.currentNetworkUsable && c.targetRouteReady && c.targetOperationSucceeded

fun internetEthernetReady(c: EthernetConditions): Boolean =
    localEthernetReady(c) && c.internetValidated

currentNetworkUsableは、その用途で必要なIF・IP構成・アクセス条件を現在の世代で確認したもの、targetOperationSucceededは現在のNetworkと期限に対応した通信結果、と定義します。過去の成功を無期限に保持せず、リンク・Network・対象条件が変わったら再評価します。UNKNOWNは別途保持し、利用許可の計算では未成立として扱います。

Q1. eth0のcarrierがUPなら、車内アプリを利用可能にしてよいですか？

解答・解説を読む

IP構成、アクセス、Networkの選択、目的の通信条件がまだ必要です。仮想carrierと物理リンクも一致するとは限りません。

Q2. VALIDATED=falseなら、車内サーバーへ必ず通信できませんか？

解答・解説を読む

そうとは限りません。公衆インターネットの検証と、車内の目的先への到達・操作成功は別です。

Q3. onAvailableでgetLinkPropertiesをすぐ再照会するのが最も確実ですか？

競合があるため、対応するonLinkPropertiesChanged等の通知引数を利用して状態を更新します。

Q4. 復帰後もIF名がeth0なら、以前のNetworkとSocketを使い続けられますか？

解答・解説を読む

保証されません。Networkの世代・接続状態と必要な構成を再確認します。

Q5. adb shellから通信できれば、すべてのアプリでも通信できますか？

解答・解説を読む

UID、restricted network、VPN、要求条件等が異なるため、その結果だけでは判定できません。

Q6. 監視コールバックを登録すると、必ずEthernetを起動・維持できますか？

解答・解説を読む

監視とNetworkの利用要求は別です。要求・設定・権限・製品ポリシーを確認します。

6. PCM読取りを実装する最小例

次のコードは公開APIのみの同期関数です。UIスレッドで動かさず、許可取得後にワーカーから呼びます。onChunkも同じワーカー上で呼ばれるため、重い処理を追加すると入力処理が遅れます。shouldContinueはスレッド間で安全に参照できるキャンセル状態を返すよう呼び出し元で実装します。

Kotlin
import android.Manifest
import android.content.Context
import android.content.pm.PackageManager
import android.media.AudioFormat
import android.media.AudioRecord
import android.media.MediaRecorder
import android.os.Looper
import android.os.SystemClock
import java.io.IOException

// 利用者の開始操作とRECORD_AUDIOの許可後に、ワーカースレッドで呼ぶ。
// 録音機能全体ではなく、最大5秒のPCM読取りだけを示す学習例。
fun capturePcmWindow(
    context: Context,
    durationMs: Long,
    shouldContinue: () -> Boolean,
    onChunk: (ShortArray) -> Unit
): Long {
    require(durationMs in 1L..5_000L)
    check(Looper.myLooper() != Looper.getMainLooper())
    if (context.checkSelfPermission(Manifest.permission.RECORD_AUDIO)
        != PackageManager.PERMISSION_GRANTED) {
        throw SecurityException("RECORD_AUDIO is required")
    }
    val rate = 16_000
    val minimumBytes = AudioRecord.getMinBufferSize(
        rate, AudioFormat.CHANNEL_IN_MONO, AudioFormat.ENCODING_PCM_16BIT)
    require(minimumBytes > 0) { "Unsupported or invalid configuration" }
    val recorder = AudioRecord.Builder()
        .setAudioSource(MediaRecorder.AudioSource.MIC)
        .setAudioFormat(AudioFormat.Builder()
            .setSampleRate(rate)
            .setChannelMask(AudioFormat.CHANNEL_IN_MONO)
            .setEncoding(AudioFormat.ENCODING_PCM_16BIT).build())
        .setBufferSizeInBytes(maxOf(minimumBytes, 3_200))
        .build()
    try {
        check(recorder.state == AudioRecord.STATE_INITIALIZED)
        recorder.startRecording()
        check(recorder.recordingState == AudioRecord.RECORDSTATE_RECORDING)
        val deadline = SystemClock.elapsedRealtime() + durationMs
        val chunk = ShortArray(320) // 16 kHz・monoでは20 ms分。
        var totalShorts = 0L
        while (SystemClock.elapsedRealtime() < deadline && shouldContinue()
            && !Thread.currentThread().isInterrupted) {
            val count = recorder.read(
                chunk, 0, chunk.size, AudioRecord.READ_NON_BLOCKING)
            when {
                count > 0 -> {
                    onChunk(chunk.copyOf(count)) // コピーでバッファ再利用と分離。
                    totalShorts += count
                }
                count == 0 -> Thread.sleep(10) // 今回はデータなし。音量ゼロとは別。
                count == AudioRecord.ERROR_DEAD_OBJECT ->
                    throw IOException("AudioRecord must be recreated")
                else -> throw IOException("AudioRecord.read failed: $count")
            }
        }
        return totalShorts
    } finally {
        try {
            if (recorder.recordingState == AudioRecord.RECORDSTATE_RECORDING) {
                recorder.stop()
            }
        } finally {
            recorder.release()
        }
    }
}

この例は保存・送信・自動再開を行いません。0.5秒で停止を要求しても、消費側の処理が長時間止まればその間は応答できません。製品ではコールバックを短くし、キュー容量・停止期限・オーバーラン・例外通知を設計します。例外時は理由を利用者へ伝え、同意やプライバシー条件が失われた録音を無条件に再開しません。

6. センサーの観測例で非同期処理を学ぶ

加速度センサーを購読する例です。車載器やVMにそのセンサーが存在するとは限らないため、未対応を返します。登録の受付と測定値の受信を分け、停止後に到着した旧世代の通知を無効化します。

Kotlin
import android.content.Context
import android.hardware.Sensor
import android.hardware.SensorEvent
import android.hardware.SensorEventListener
import android.hardware.SensorManager
import android.os.Handler
import android.os.Looper

// start/stopと通知をメインスレッドへそろえた、加速度センサーの観測例。
class AccelerationObserver(context: Context) {
    private val manager = context.applicationContext
        .getSystemService(SensorManager::class.java)
    private val handler = Handler(Looper.getMainLooper())
    private var listener: SensorEventListener? = null
    private var generation = 0L

    fun start(onSample: (Long, FloatArray, Int) -> Unit): Boolean {
        check(Looper.myLooper() == Looper.getMainLooper())
        if (listener != null) return true
        val sm = manager ?: return false
        val sensor = sm.getDefaultSensor(Sensor.TYPE_ACCELEROMETER) ?: return false
        val mine = ++generation
        val candidate = object : SensorEventListener {
            override fun onSensorChanged(event: SensorEvent) {
                if (mine != generation) return
                // valuesは再利用され得るので、保持する場合はコピーする。
                onSample(event.timestamp, event.values.copyOf(), event.accuracy)
            }
            override fun onAccuracyChanged(sensor: Sensor?, accuracy: Int) = Unit
        }
        val accepted = sm.registerListener(
            candidate, sensor, SensorManager.SENSOR_DELAY_NORMAL, handler)
        if (accepted) listener = candidate else ++generation
        return accepted // 登録受付。最初の測定値の受信とは別。
    }

    fun stop() {
        check(Looper.myLooper() == Looper.getMainLooper())
        ++generation // 旧世代の遅延通知を無効化。
        listener?.let { manager?.unregisterListener(it) }
        listener = null
    }
}

SENSOR_DELAY_NORMALは要求の目安で、正確な周期の保証ではありません。SensorEvent.timestampは壁時計の日時ではなく、elapsedRealtimeNanosと対応する単調な時刻基準のナノ秒値です。保持するvaluesはコピーし、accuracy・座標系・単位・データの鮮度も確認します。この加速度例を、body sensors等の権限条件が違う全センサーへそのまま適用しません。画面表示との連携ではstart/stopを適切なライフサイクルに合わせ、停止を忘れないようにします。

7. 起動・画面OFF・サスペンド・終了を対応付ける

車載器の状態Android／機器で分ける状態基本設計の確認事項
起動中サービス公開・HAL接続・ドライバ認識・機器準備一つの起動完了イベントで全機器READYにしない
画面OFFアプリ可視性・機器の必要性・入力継続可否表示停止を全機器電源OFFと同一視しない
EVのサスペンド準備要求の受付制限・処理中要求・保存・機器停止受付停止、完了待ちの期限、失効範囲を機能別に定義
EVのレジュームサービス接続・機器再初期化・経路・観測の鮮度復帰後の世代で再評価。全機器に同じ復帰順序を仮定しない
エンジン車の終了停止意図・処理中要求・リソース解放・電源断期限内に確定できない処理と次回起動時の整合を設計
機器切断／サービス再起動機能利用不可・再接続・前回要求の扱い古いREADYと要求応答を失効し、必要な状態を再取得
ユーザー・利用条件変更権限・対象機器・用途の制限接続を維持していても利用許可を再判定

AndroidのPowerManager、HALの機器状態、ゲストカーネルの電源管理、QNXホストの実機制御は同一の状態機械ではありません。どの機器を維持・停止するか、Androidへ何が通知されるかは製品の契約へ残し、ここではAndroid内の要求と観測の失効・再確認を定義します。

8. VM構成で追加する観測軸

Android側では「API利用可」「サービス接続」「ゲスト側の機器準備」「外部への接続」「物理機器の観測」を分けます。ゲストのドライバがREADYでも、ホスト側や外部機器の準備が未完了の場合があります。具体的な所有主体、仮想化方式、復帰通知の契約は、この資料のAndroid内状態整理から切り出して後続の責務検討へ引き渡します。

理解を確かめる

Q1. アプリをNative化すると/devやGPIOを自由に操作できますか？

解答・解説を読む

できません。UID、SELinux、ドライバ等の権限・アクセス条件は残ります。利用可能な公開APIや製品サービスを確認します。

Q2. 制御APIが成功を返したら、物理動作も完了していますか？

解答・解説を読む

そのAPIの成功の定義次第です。受付・反映・観測・実動作確認を契約で区別します。

Q3. 全ての機器へ独自AIDL HALを作りますか？

解答・解説を読む

既存の公開API・サービス・標準HAL等を先に確認します。機能ごとに必要な境界を選びます。

Q4. VHALは一般アプリへ任意のレジスタ書込みを提供する仕組みですか？

解答・解説を読む

違います。車両プロパティを扱う境界です。対応プロパティ、権限、アクセス属性、area等を確認します。

Q5. 要求がTIMEOUTしたので同じ動作をすぐ再実行してよいですか？

解答・解説を読む

無条件には再実行しません。既に作用した可能性、現在値、重複時の副作用、旧応答の扱いを確認します。

Q6. センサー登録がtrueなら、測定値も取得済みですか？

解答・解説を読む

登録受付とイベント受信は別です。最初の値と鮮度・品質を確認して利用可能を判断します。
