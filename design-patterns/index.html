CHAPTER 01 / 導入

学び方と設計の基礎

覚えるのは名前より、変更を受け止める場所。23の設計パターンを、問題・依存関係・コード・判断の順で学びます。

GoF 23パターンJava 17図23点確認問題46問

この教材の読み方

クラス・インターフェース・継承の基本が前提です。まず適用前のコードを読み、変更要求で困る場所を考えてください。次に図と適用後を対応させ、利点より先に「追加した型と依存」を数えます。最後に解答を開かず確認問題へ進みます。全章を順番に読むほか、比較表から悩んでいる設計へ移動できます。

生成は「誰が何を作るか」、構造は「何と何をつなぐか」、振る舞いは「誰が判断して処理するか」を扱います。同じクラス図に見えても、解決したい問題が違えば名前も採用判断も変わります。

凝集度・結合度・委譲

凝集度は、一つの部品の責務がどれだけ一貫しているか。注文の検証と画面の配色を同じクラスへ入れると変更理由が増えます。結合度は、他の部品の詳細へどれだけ依存するか。外部APIの型や呼出順が多くの場所へ漏れると変更が波及します。インターフェースに依存しても、意味や呼出順への依存は残ります。

委譲は自分が受けた仕事を別オブジェクトへ依頼すること。継承は共通の型と実装を親から受け継ぎ、合成は他オブジェクトをフィールドとして持ちます。継承は親の契約に従う自然な置換関係があるときに使い、実行時に交換したい処理は合成を検討します。「常に合成が正解」という規則ではありません。

変更点を分離する

会員割引の追加を想像してください。注文全体を継承するより、料金計算だけをPricingへ切り出すと注文受付は変えずに済みます。一方、割引が今後増えず一か所の条件分岐で済むなら、型を増やす利点は小さくなります。変更の頻度・範囲・テストのしやすさを根拠に判断します。

原則パターンとの接点誤用を避ける視点
S：単一責任FacadeやMediatorで調整の責務を集める全業務を巨大な窓口へ詰め込まない
O：開放閉鎖StrategyやDecoratorで実装を追加するすべての変更から閉じるのは不可能。守る変更軸を選ぶ
L：リスコフ置換共通インターフェースで具体型を扱う型が同じでも事前条件・例外・副作用が違えば置換できない
I：インターフェース分離利用者に必要な操作だけを公開するCompositeの葉へ無意味なaddを押しつけない
D：依存性逆転通知側が具体的SMSではなくSenderを使うインターフェースを増やすだけで意味的な依存が消えるわけではない

全コードはJava 17の言語・標準APIを基準にしています。適用前は問題を示す小さな正常系、適用後は独立した実行例です。各コードをそれぞれ別ディレクトリのMain.javaへ保存し、JDK 17以降で下記を実行します。同じ名前の型が章ごとに出るため、複数章を一つのファイルへ連結しないでください。

CHAPTER 02 / 生成

Abstract Factory｜関連する製品群をまとめて生成する

関連する製品群をまとめて生成する。

この章の到達点Abstract Factoryの役割と採用条件を、変更要求から説明できる。
分類・前提生成／導入の基礎とJavaのクラス・インターフェース

問題と変更要求

画面のボタンとチェックボックスを個別に生成すると、異なるテーマの部品を混ぜられてしまう。

追加する要求：ライト用の部品に加えて、ダーク用の部品一式を追加する。

適用前：Main.java（問題を絞った正常系）
public class Main {
    public static void main(String[] args) {
        class LightButton { String draw() { return "light button"; } }
        class DarkCheck { String draw() { return "dark check"; } }
        LightButton button = new LightButton();
        DarkCheck check = new DarkCheck(); // 個別生成ではテーマが混ざる
        System.out.println(button.draw() + " / " + check.draw());
    }
}

設計を変える

適用後と使用例：Main.java（Java 17）
public class Main {
    interface Button { String draw(); }
    interface Check { String draw(); }
    interface Theme {
        Button button();
        Check check();
    }
    static class Light implements Theme {
        public Button button() { return () -> "light button"; }
        public Check check() { return () -> "light check"; }
    }
    static class Dark implements Theme {
        public Button button() { return () -> "dark button"; }
        public Check check() { return () -> "dark check"; }
    }
    static void screen(Theme theme) {
        System.out.println(theme.button().draw() + " / " + theme.check().draw());
    }
    public static void main(String[] args) { screen(new Dark()); }
}
実行結果
dark button / dark check

変更に強くなった場所

画面処理を変えずにThemeの実装を追加できる。テーマごとの整合性を一つの生成元へ集められる。ただし同じThemeから取得する規約も必要。

コスト・前提・使わない判断

製品の種類にSliderを増やすとThemeと全テーマ実装の変更が必要。関連する製品群がなければコンストラクタで十分。

似たパターンとの違い

Factory Methodはサブクラスが生成を差し替える仕組み。Abstract Factoryは製品群を生成する窓口で、内部にFactory Methodを使うこともある。

理解を確かめる

Q1. テーマ追加時にscreenを書き換える必要はある？

ない。Themeに依存するため、組立箇所でDarkを選べば画面処理は共通にできる。

Q2. Slider追加も変更箇所が一つに収まる？

収まらない。製品種別を追加すると窓口と全製品群が影響を受ける。

CHAPTER 03 / 生成

Builder｜複雑な生成手順と完成品を分離する

複雑な生成手順と完成品を分離する。

この章の到達点Builderの役割と採用条件を、変更要求から説明できる。
分類・前提生成／導入の基礎とJavaのクラス・インターフェース

問題と変更要求

レポートのヘッダー・本文・末尾を呼出側が文字列結合しており、別形式の生成手順にも同じ順序が重複する。

追加する要求：同じ集計手順からテキスト形式とHTML形式を出力する。

適用前：Main.java（問題を絞った正常系）
public class Main {
    public static void main(String[] args) {
        String report = "TITLE: Sales\n" + "TOTAL: 120\n" + "END";
        System.out.println(report);
    }
}

設計を変える

適用後と使用例：Main.java（Java 17）
public class Main {
    interface ReportBuilder {
        void title(String text);
        void total(int value);
        void end();
        String result();
    }
    static class TextBuilder implements ReportBuilder {
        private final StringBuilder out = new StringBuilder();
        public void title(String s) { out.append("TITLE: ").append(s).append("\n"); }
        public void total(int n) { out.append("TOTAL: ").append(n).append("\n"); }
        public void end() { out.append("END"); }
        public String result() { return out.toString(); }
    }
    static class HtmlBuilder implements ReportBuilder {
        private final StringBuilder out = new StringBuilder();
        public void title(String s) { out.append("<h1>").append(s).append("</h1>"); }
        public void total(int n) { out.append("<p>").append(n).append("</p>"); }
        public void end() { out.append("<!-- end -->"); }
        public String result() { return out.toString(); }
    }
    static class ReportDirector {
        void construct(ReportBuilder b) {
            b.title("Sales"); b.total(120); b.end();
        }
    }
    public static void main(String[] args) {
        ReportBuilder b = new TextBuilder();
        new ReportDirector().construct(b);
        System.out.println(b.result());
    }
}
実行結果
TITLE: Sales
TOTAL: 120
END

変更に強くなった場所

生成順序はDirector、表現は各Builderに分離される。HTML追加時に集計手順を複製せずに済む。

コスト・前提・使わない判断

途中状態の扱いや再利用の可否を決める必要がある。この例は1インスタンス1回の生成を想定し、HTMLの動的入力にはエスケープが必要。数項目の不変オブジェクトならコンストラクタやrecordが簡潔。

似たパターンとの違い

Abstract Factoryは関連製品の生成窓口。Builderは複数段階の組立を制御する。Javaでよく見る流暢な設定APIだけがGoF Builderではない。

理解を確かめる

Q1. HTML対応でDirectorを複製する？

不要。同じReportBuilderの操作列を別の具体Builderへ渡せる。

Q2. 同じBuilderでconstructを2回呼ぶと？

この実装は追記する。再利用したいならリセットや生成後の状態管理を別途定義する。

CHAPTER 04 / 生成

Factory Method｜生成をサブクラスの判断に委ねる

生成をサブクラスの判断に委ねる。

この章の到達点Factory Methodの役割と採用条件を、変更要求から説明できる。
分類・前提生成／導入の基礎とJavaのクラス・インターフェース

問題と変更要求

インポート処理の共通手順がCSVパーサーのコンストラクタへ直接依存している。

追加する要求：前後処理は共通に保ち、JSONの読取も追加する。

適用前：Main.java（問題を絞った正常系）
public class Main {
    public static void main(String[] args) {
        class CsvParser { String parse() { return "CSV parsed"; } }
        class Importer {
            void run() {
                CsvParser parser = new CsvParser(); // 生成先が固定
                System.out.println("open -> " + parser.parse() + " -> close");
            }
        }
        new Importer().run();
    }
}

設計を変える

適用後と使用例：Main.java（Java 17）
public class Main {
    interface Parser { String parse(); }
    static class CsvParser implements Parser {
        public String parse() { return "CSV parsed"; }
    }
    static class JsonParser implements Parser {
        public String parse() { return "JSON parsed"; }
    }
    static abstract class Importer {
        protected abstract Parser createParser(); // Factory Method
        final void run() {
            System.out.println("open -> " + createParser().parse() + " -> close");
        }
    }
    static class CsvImporter extends Importer {
        protected Parser createParser() { return new CsvParser(); }
    }
    static class JsonImporter extends Importer {
        protected Parser createParser() { return new JsonParser(); }
    }
    public static void main(String[] args) { new JsonImporter().run(); }
}
実行結果
open -> JSON parsed -> close

変更に強くなった場所

共通処理を継承したまま生成するParserを差し替えられる。依存先の具体型をサブクラスへ移せる。

コスト・前提・使わない判断

製品ごとにImporterのサブクラスが増える。生成差替えだけならParserをコンストラクタ引数で受ける方が単純なこともある。

似たパターンとの違い

単なるstatic of()やswitchを持つ生成関数とは区別する。GoF Factory Methodの中心は継承とオーバーライドによる生成の差替え。Template Methodと組み合わせやすい。

理解を確かめる

Q1. createParserをstaticにすると同じ仕組みになる？

ならない。staticメソッドは動的ディスパッチでオーバーライドされず、この継承上の差替えを失う。

Q2. 共通のrunはJSONの具体型を知る？

知らない。Parser契約を使い、具体的な生成はJsonImporterが担当する。

Prototype｜既存のひな型から独立した複製を作る

既存のひな型から独立した複製を作る。

この章の到達点Prototypeの役割と採用条件を、変更要求から説明できる。
分類・前提生成／導入の基礎とJavaのクラス・インターフェース

問題と変更要求

帳票テンプレートと同じ設定を新規作成するたびに、呼出側が内部構造を知ってコピーしている。

追加する要求：ひな型のタグ一覧を複製し、一方だけにタグを追加する。

適用前：Main.java（問題を絞った正常系）
public class Main {
    public static void main(String[] args) {
        var tags = new java.util.ArrayList<>(java.util.List.of("base"));
        var copy = tags; // コピーのつもりで参照を共有
        copy.add("urgent");
        System.out.println(tags);
    }
}

設計を変える

適用後と使用例：Main.java（Java 17）
public class Main {
    interface Prototype { Prototype copy(); }
    static class Template implements Prototype {
        private final java.util.List<String> tags;
        Template(java.util.List<String> tags) {
            this.tags = new java.util.ArrayList<>(tags);
        }
        public Template copy() { return new Template(tags); }
        void add(String tag) { tags.add(tag); }
        String describe() { return tags.toString(); }
    }
    public static void main(String[] args) {
        Template base = new Template(java.util.List.of("base"));
        Template copy = base.copy();
        copy.add("urgent");
        System.out.println(base.describe());
        System.out.println(copy.describe());
    }
}
実行結果
[base]
[base, urgent]

変更に強くなった場所

複製の知識をTemplateに閉じ込められ、呼出側は初期化の詳細を知らずに既存設定を基にできる。

コスト・前提・使わない判断

深いコピーの境界と循環参照を設計する必要がある。この例ではStringは不変なのでリストを複製すればよい。共有資源や接続を無条件にコピーしない。生成が簡単ならnewで十分。

似たパターンとの違い

Builderは段階的に組み立て、Prototypeは完成済みのひな型を複製する。Object.cloneを使うことは必須でない。

理解を確かめる

Q1. リストの代入だけで独立する？

しない。同じ可変リストを共有するため、片方の変更がもう片方にも見える。

Q2. 要素が可変オブジェクトならこのcopyで十分？

独立させたい要素も複製する必要がある。浅いコピーと深いコピーの境界を契約に明記する。

Singleton｜生成数を制限し共通の取得口を提供する

生成数を制限し共通の取得口を提供する。

この章の到達点Singletonの役割と採用条件を、変更要求から説明できる。
分類・前提生成／導入の基礎とJavaのクラス・インターフェース

問題と変更要求

変更されない既定設定をどこでもnewしており、同一インスタンスという要件を守れない。

追加する要求：プロセス内の同じクラスローダーでは既定設定を一つに限定する。

適用前：Main.java（問題を絞った正常系）
public class Main {
    public static void main(String[] args) {
        Object first = new Object();
        Object second = new Object();
        System.out.println(first == second);
    }
}

設計を変える

適用後と使用例：Main.java（Java 17）
public class Main {
    enum Defaults {
        INSTANCE;
        String region() { return "JP"; }
    }
    public static void main(String[] args) {
        Defaults a = Defaults.INSTANCE;
        Defaults b = Defaults.INSTANCE;
        System.out.println(a == b);
        System.out.println(a.region());
    }
}
実行結果
true
JP

変更に強くなった場所

enumの初期化により安全に単一インスタンスを公開できる。この例は可変データを持たないので共有更新の競合もない。

コスト・前提・使わない判断

単一性はクラスローダー単位であり別プロセスまでは及ばない。可変フィールドの更新が自動的にスレッド安全になるわけではない。グローバルな依存はテスト差替えや並列実行を難しくするため、通常は組立側で一つ作り依存注入する案も検討する。

似たパターンとの違い

単にアプリ起動時に一つ作って渡す設計は、型自身が生成制限するSingletonとは異なる。Flyweightの共有対象は複数種類の値でもよい。

理解を確かめる

Q1. enumなら内部のArrayListへの同時追加も安全？

安全ではない。初期化の安全性と可変状態の並行操作は別で、同期や不変化などが必要。

Q2. テストごとに別設定を使いたい場合は？

インターフェース経由で設定を注入する方が差替えやすい。Singletonが本当に必要か再検討する。

CHAPTER 07 / 構造

Adapter｜既存APIを利用側の契約へ変換する

既存APIを利用側の契約へ変換する。

この章の到達点Adapterの役割と採用条件を、変更要求から説明できる。
分類・前提構造／導入の基礎とJavaのクラス・インターフェース

問題と変更要求

通知側はsend(String)を使いたいが、既存SMSライブラリの操作はpost(String)になっている。

追加する要求：SMS実装を変えずに、新しい通知サービスから利用する。

適用前：Main.java（問題を絞った正常系）
public class Main {
    public static void main(String[] args) {
        class LegacySms { void post(String s) { System.out.println("SMS: " + s); } }
        LegacySms sms = new LegacySms();
        sms.post("ready"); // 呼出側が外部APIを直接知る
    }
}

設計を変える

適用後と使用例：Main.java（Java 17）
public class Main {
    interface Sender { void send(String text); }
    static class LegacySms {
        void post(String payload) { System.out.println("SMS: " + payload); }
    }
    static class SmsAdapter implements Sender {
        private final LegacySms legacy;
        SmsAdapter(LegacySms legacy) { this.legacy = legacy; }
        public void send(String text) { legacy.post(text); }
    }
    public static void main(String[] args) {
        Sender sender = new SmsAdapter(new LegacySms());
        sender.send("ready");
    }
}
実行結果
SMS: ready

変更に強くなった場所

利用側はSenderだけに依存する。外部APIの差異や引数変換をAdapterへ局所化できる。

コスト・前提・使わない判断

名前を変えるだけでは意味の互換性は保証しない。単位・例外・同期非同期の差も調整する必要がある。既存APIがそのまま契約を満たすなら不要。

似たパターンとの違い

Bridgeは最初から二つの変化軸を分離する設計。Adapterは既存の不一致を橋渡しする。Facadeは複雑な操作群の窓口を作る。

理解を確かめる

Q1. postが非同期でも単に呼べばsend完了を保証できる？

できない。sendの契約が受付か送信完了かを定め、必要なら非同期の結果も変換する。

Q2. LegacySms自体を編集する必要は？

不要。合成によるAdapterが既存インスタンスを包んでいる。

CHAPTER 08 / 構造

Bridge｜抽象側と実装側の変化軸を分離する

抽象側と実装側の変化軸を分離する。

この章の到達点Bridgeの役割と採用条件を、変更要求から説明できる。
分類・前提構造／導入の基礎とJavaのクラス・インターフェース

問題と変更要求

緊急通知・通常通知と、メール・SMSの組合せごとにサブクラスを作ると種類が掛け算で増える。

追加する要求：通知の優先度と送信手段を独立に追加する。

適用前：Main.java（問題を絞った正常系）
public class Main {
    public static void main(String[] args) {
        class UrgentSms {
            void publish(String text) { System.out.println("SMS: URGENT: " + text); }
        }
        class NormalMail {
            void publish(String text) { System.out.println("MAIL: " + text); }
        }
        new UrgentSms().publish("fire");
        new NormalMail().publish("ready");
        // UrgentMailやNormalSmsも同じ形で増え、組合せが型になる
    }
}

設計を変える

適用後と使用例：Main.java（Java 17）
public class Main {
    interface Channel { void send(String text); }
    static class Mail implements Channel {
        public void send(String s) { System.out.println("MAIL: " + s); }
    }
    static class Sms implements Channel {
        public void send(String s) { System.out.println("SMS: " + s); }
    }
    static abstract class Notice {
        protected final Channel channel;

    static class Append implements Command {
        private final StringBuilder doc;
        private final String text;
        private int oldLength;
        Append(StringBuilder doc, String text) { this.doc=doc; this.text=text; }
        public void execute() { oldLength=doc.length(); doc.append(text); }
        public void undo() { doc.setLength(oldLength); }
    }
    static class History {
        private final java.util.Deque<Command> done = new java.util.ArrayDeque<>();
        void run(Command c) { c.execute(); done.push(c); }
        void undo() { if (!done.isEmpty()) done.pop().undo(); }
    }

        StringBuilder doc = new StringBuilder("A");
        History history = new History();
        history.run(new Append(doc, "B"));
        System.out.println(doc);
        history.undo(); System.out.println(doc);
    }
}

    static class Events {
        private final java.util.List<Listener> listeners = new java.util.ArrayList<>();
        void subscribe(Listener l) { if (!listeners.contains(l)) listeners.add(l); }
        void unsubscribe(Listener l) { listeners.remove(l); }
        void publish(String event) {
            for (Listener l : java.util.List.copyOf(listeners)) {

                catch (RuntimeException ex) { System.out.println("listener failed"); }

        events.subscribe(mail);
        events.subscribe(e -> { throw new IllegalStateException("offline"); });

        events.publish("paid");
        events.unsubscribe(mail);
        events.publish("shipped");
    }

public class Main {

    record Circle(int radius) implements Shape {
        public String accept(Visitor v) { return v.visit(this); }
    }
    record Rectangle(int width, int height) implements Shape {
        public String accept(Visitor v) { return v.visit(this); }
    }
    interface Visitor {
        String visit(Circle c);
        String visit(Rectangle r);
    }
    static class Describe implements Visitor {
        public String visit(Circle c) { return "circle radius=" + c.radius(); }
        public String visit(Rectangle r) { return "rectangle " + r.width() + "x" + r.height(); }
    }
    public static void main(String[] args) {
        Visitor describe = new Describe();
        for (Shape s : java.util.List.of(new Circle(2), new Rectangle(3,4))) {
            System.out.println(s.accept(describe));
        }
    }
}
実行結果
circle radius=2
rectangle 3x4

変更に強くなった場所

要素の種類が安定していれば、面積や検査など新しい操作を別Visitorとして追加できる。要素の型判定を各処理へ散らさずに済む。

コスト・前提・使わない判断

新しいTriangleを増やすとVisitorと全実装を変更する。外部の操作に必要な状態公開が増えることもある。型が頻繁に増える、操作が一つだけなら通常の多態メソッドが簡潔。

似たパターンとの違い

Iteratorは要素の列挙、Visitorは型ごとの処理を分離する。この例のList走査はIteratorであり、Visitor自体に走査機能があるわけではない。

理解を確かめる

Q1. 面積計算の追加でCircleのacceptを修正する？

Visitor契約を実装する新しい処理を作れば、既存のacceptはそのまま使える。戻り値型はこの例ではStringに固定している。

Q2. Triangle追加時の影響は？

visit(Triangle)とTriangle.acceptに加え、全Visitor実装へ対応を追加する。要素種類の安定性が採用判断になる。

類似パターンの比較と選び方

「似た図だから同じ」ではありません。目的・変化する軸・変更時に触る場所を比べます。

比較判断の質問具体例
Abstract Factory / Factory Method製品群の整合性か、生成フックの差替えかテーマ一式ならAbstract Factory。共通の読取手順から生成だけをサブクラスで変えるならFactory Method。
Bridge / Adapter二つの拡張軸か、既存契約の不一致か通知種別×媒体を独立拡張するならBridge。既存postをsendとして扱うならAdapter。
Decorator / Proxy責務を重ねるか、実体へのアクセスを制御するか加工とログを任意に重ねるならDecorator。読込遅延やアクセス権ならProxy。構造が似ていても意図を確認する。
State / Strategyライフサイクル上の遷移か、同じ目的の手段の選択か未払い→支払い済みならState。通常料金と会員料金を組立時に選ぶならStrategy。
Strategy / Template Method合成でアルゴリズムを交換するか、継承で手順の一部を変えるか実行ごとの交換や独立テストを重視するならStrategy。安定した手順と自然な継承関係ならTemplate Method。
Composite / Decorator子をまとめるか、一つの対象に責務を加えるかフォルダーの再帰集計ならComposite。単一送信器へのログ付与ならDecorator。
Mediator / Observer協調ルールか、変更通知の機構かフォーム全体の整合を保つならMediator。独立した通知先への配信ならObserver。併用もできる。
Command / Memento要求を記録するか、状態を保存するか操作の再実行やキューならCommand。内部状態の保存復元ならMemento。取消処理で組合せることもある。
Builder / Prototype段階的な組立か、既存インスタンスからの複製か同じ生成手順で形式を変えるならBuilder。実行時に選んだひな型を複製するならPrototype。

採用前に答える五つの質問

  1. 今ある変更要求は何か。予想だけでなく実例を挙げられるか。
  2. 分離する変化軸は何か。どのクラスを変更から守りたいか。
  3. 増える型・依存・組立・デバッグのコストは許容できるか。
  4. 単純なif、関数引数、標準ライブラリで十分ではないか。
  5. 例外・並行性・寿命の契約を、追加した境界で説明できるか。

Android補足：外部SDKを自アプリの契約へ合わせる場面はAdapter、画面部品の協調はMediator、イベントの購読はObserverとして考えられます。ただしAPI名にFactoryやBuilderが含まれているだけでGoFの役割に一致するとは限りません。ライフサイクルに合わせた購読解除も確認します。

CHAPTER 26 / 応用

総合演習：注文通知を育てる

題材は注文確定後の通知です。完成形から逆算せず、要求が増える段階ごとに最小の変更案を比較します。

段階1：メールを一通送る

注文確定後に一つのメール関数を呼ぶだけなら、そのままで十分です。将来必要かもしれないという理由だけで23パターンを導入しません。送信完了・失敗の意味を先に定義します。

段階2：メールとSMSを顧客ごとに選ぶ

Channel契約へ送信処理を分け、組立側でMailかSmsを選ぶStrategyを候補にします。既存SMSの操作がpostしかないなら、その実装内にAdapterを置きます。媒体だけを交換する段階では、二つの階層を用意するBridgeや製品群のAbstract Factoryはまだ必要ありません。

段階3：一部の送信にだけログを付ける

Logging Decoratorで選んだChannelを包みます。ログが全送信に必須で一か所だけなら通常の送信メソッド内でも十分です。ログの出力は配送成功を意味しません。本文や個人情報をログへ残す要件も検討します。

段階4：受付と実行を分ける

宛先を表すID・本文・送信手段をSendCommandにまとめ、Dispatcherへ預けます。ここでCommandはundoを実装しません。送信済みの通知は取り消せないからです。通知方策の交換がStrategy、特定の通知要求を保持するのがCommandです。

総合演習：Main.java（Java 17）
public class Main {
    interface Channel { void send(String id, String text); }
    static class Mail implements Channel {
        public void send(String id, String text) { System.out.println("MAIL " + id + ": " + text); }
    }
    static class Sms implements Channel {
        public void send(String id, String text) { System.out.println("SMS " + id + ": " + text); }
    }
    static class Logging implements Channel {
        private final Channel next;
        Logging(Channel next) { this.next=next; }
        public void send(String id, String text) {
            System.out.println("LOG " + id); next.send(id, text);
        }
    }
    record SendCommand(Channel channel, String id, String text) {
        void execute() { channel.send(id, text); }
    }
    static class Dispatcher {
        private final java.util.Queue<SendCommand> queue = new java.util.ArrayDeque<>();
        void enqueue(SendCommand c) { queue.add(c); }
        void drain() {
            while (!queue.isEmpty()) queue.remove().execute();
        }
    }
    public static void main(String[] args) {
        Channel channel = new Logging(new Sms());
        Dispatcher dispatcher = new Dispatcher();
        dispatcher.enqueue(new SendCommand(channel, "order-7", "paid"));
        System.out.println("queued");
        dispatcher.drain();
    }
}
実行結果
queued
LOG order-7
SMS order-7: paid

段階5：本番の配送保証を要求されたら

このキューはプロセス終了で消えます。drainは実行前に要求を取り出すため、例外時には再投入されません。永続的なキュー、再試行回数・間隔、重複抑止、送信先との冪等性を追加設計します。Commandを作っただけでは一度だけの配送は保証されません。注文確定と通知登録の整合性にはトランザクショナルアウトボックス等も検討します。

監査や分析など複数の独立した反応が必要ならObserverを候補にしますが、同じ顧客への送信手段の選択とは分けます。配送の状態管理が複雑化した時点でStateも検討できます。現時点で固定のqueued / done / failedだけならenumによる状態管理も有効です。

設計を説明する演習

  1. Push通知を追加し、注文処理へ媒体の分岐を入れずに済む変更箇所を列挙してください。
  2. ログを送信前と成功後のどちらへ出すか決め、失敗時の観測結果を説明してください。
  3. 送信後に接続が切れた場合の再試行で、重複送信をどう扱うか設計してください。
設計例と採用しなかった案を読む

PushはChannelの実装を追加し組立側で選びます。SDKとの契約が異なるならAdapterを内側へ置きます。ログは受付と成功を分けたイベントにすると誤認を減らせます。再試行では安定した要求IDと送信先での重複抑止が必要で、IDを渡すだけでは保証になりません。相手が冪等性を提供しない場合は重複許容・照合・手動確認を含めて判断します。媒体ごとの送信しかないためAbstract Factoryは採用せず、通知の優先度も独立拡張しない段階ではBridgeも採用しません。要求の規模が小さければDecoratorやCommandを省き、一つのサービスへまとめる設計も説明可能です。
