図の読み方

  1. 各図の「登場する役割」を読み、説明シナリオを選びます。
  2. まず静止した矢印と番号付き手順を上から読みます。横の列は役割、縦の並びは呼出の順序です。厳密なUML図ではありません。
  3. 「再生する」を選ぶと、ラベル付きの印が矢印の上を順に移動し、処理先の枠に▶印が出ます。もう一度選択を外すと、その位置で一時停止します。
  4. 実線は呼出・通知・状態更新、破線は戻りです。印の文字と矢印番号でも意味を区別します。
  5. 動く図を止めて、結果と「よくある誤解」を読み、確認問題へ進みます。
この教材はCSSで事前に決めた説明を再生します。Javaのオブジェクト生成、送信、決済などの業務処理を実行するものではありません。役割名の列が必ず別のインスタンスを表すわけでもありません。各図の省略事項と前提を確認してください。

狭い画面では、図の文字を縮めず図だけを横スクロールします。動きを減らす設定ではアニメーションを停止し、同じ矢印と番号付き手順を表示します。印刷はブラウザの印刷機能を使ってください。すべてのシナリオ・結果・解答を静止した状態で印刷できます。

必要な前提は、クラス・インターフェース・委譲の基礎です。詳細なJavaコードや採用しない判断はGoFデザインパターン体系学習ガイドで学べます。

同じラッパーを使っても順序は交換可能とは限らない。Proxyも対象を包むが、主目的はアクセス制御や遅延取得などで、Decoratorは責務の追加に着目する。

理解を確かめる

Loggingの外側にUpperを置くと、ログに残る本文はどう変わる？

Upperが先に大文字へ変えるためLoggingにもREADYが渡る。逆の順序ではログはready、Mailへ渡る本文はREADYになる。

ANIMATION 04

State
操作の結果を現在の状態へ委ねる

解決したい問題

注文の各操作に状態のif分岐が散らばっている。状態ごとの許可操作と遷移を各Stateへまとめ、Orderが現在の状態へ委譲する。

登場する役割

利用者
発送要求・支払要求を順に送る。
Order / Context
現在のStateを保持し、操作を委譲する。
Unpaid
発送を拒否し、支払時にPaidへ遷移させる。
Paid / Shipped
Paidは発送でShippedへ遷移。Shippedは発送済みの状態。

この図で省略していること

決済サービス、排他制御、永続化、発送済み状態での再操作は省略。状態更新と実際の外部処理を一体で保証するものではない。

よくある誤解

Stateは状態と遷移に応じた振る舞いを表す。Strategyの方策選択と図形が似ていても意図が違う。クラスを分けるだけでは二重決済や同時更新は防げない。

理解を確かめる

二回のship()で結果が違う理由は？

最初はUnpaidへ委譲されて拒否され、支払い後はPaidへ委譲されて発送へ進むため。同じ操作でも、現在のStateにより振る舞いが変わる。

確認問題：二回のship()で結果が違う理由は？

最初はUnpaidへ委譲されて拒否され、支払い後はPaidへ委譲されて発送へ進むため。同じ操作でも、現在のStateにより振る舞いが変わる。

ANIMATION 05

Factory Method
共通手順から、生成フックを呼び出す

解決したい問題

共通のインポート処理が具体的なParserのnewへ直接依存している。手順を親に残し、生成をサブクラスのオーバーライドへ委ねる。

登場する役割

利用者
具体的なImporterを選んでrunを呼ぶ。
Importer.run
共通手順の中でcreateParserを呼び、その結果でparseを実行する。
具体Importer.createParser
CSVまたはJSON用の生成メソッドをオーバーライドする。
具体Parser
生成された製品としてparseを提供する。

切替は用意した説明シナリオの選択です。切替先は初めから再生します。停止中の切替先は初期状態で停止します。

この図で省略していること

ファイルの開閉、構文解析の内部、例外時の後始末とparseの戻りは省略。Importer.runと具体Importer.createParserの列は、同じオブジェクト内の異なる役割を分けたもので、別インスタンスではない。

よくある誤解

staticなof()や単なる生成用関数すべてをGoF Factory Methodと呼ぶわけではない。ここでの中心は、共通処理から呼ぶ生成メソッドをサブクラスがオーバーライドすること。

理解を確かめる

共通のrun()がCSVとJSONをswitchで選ぶ必要はある？

ない。runはcreateParserを呼び、実際のImporterに応じたオーバーライドへ動的にディスパッチされる。返ったParserの共通契約を使って後続処理を進める。

確認問題：共通のrun()がCSVとJSONをswitchで選ぶ必要はある？

ない。runはcreateParserを呼び、実際のImporterに応じたオーバーライドへ動的にディスパッチされる。返ったParserの共通契約を使って後続処理を進める。
