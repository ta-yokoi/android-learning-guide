CHAPTER 01

01. 組み込みシステムの全体像

この章で分かることMCU・SoC・OSの役割と、製品の正しさ・期限・資源を説明できる。
前提知識プログラミングの変数・関数の基礎。

組み込みシステムは、機器の中で決まった目的を実現するコンピューターです。温度を測ってファンを制御する製品なら、測定・判断・出力・故障時の対応までが機能です。プログラムの計算結果が正しいことに加え、必要な時刻に実際の機器へ作用したかを確認します。

1. 製品を入力・判断・出力で読む

区分よくある特徴選択時の確認
MCU（マイコン）CPU・RAM・Flash・周辺回路を一つのチップへ集積する例が多いメモリ量、電力、応答期限、周辺機能、開発環境
SoC複数コア、画像・音声処理、外部DRAM等を組み合わせる例帯域、起動時間、複数OS、BSP、熱・電力
ベアメタル一般的なOSを使わず初期化と実行順序を組む処理の分割、期限、割込みと共有データ
RTOS優先度等に基づいてタスクを実行するOS設定、最悪応答時間、競合、スタック
組み込みLinuxプロセス分離や豊富なドライバ・ネットワーク機能メモリ、起動、設定、長時間動作、期限の検証

MCUとSoCの境界は厳密な二分ではありません。名称だけで性能・OS・リアルタイム性を決めず、要求と実装を照合します。ファームウェアは機器へ組み込むソフトウェアを指す言葉で、OSがないプログラムだけの呼称ではありません。

2. リアルタイム性と資源制約

要求定義する例証拠
正しさ温度の単位、範囲、制御条件が正しい境界値・異常値の試験
期限入力の成立から20 ms以内に出力を確認起点・終点・時計を定めた計測
資源RAM・Flash・CPU時間・帯域に収まるmap、最大使用量、負荷条件
信頼性長時間・再起動・通信異常でも機能を維持故障注入、継続試験、復旧の記録

「速い」は平均の処理時間の話にもなりますが、「期限を守る」は遅い場合も含む要求です。hard／soft real-timeの区分は期限を外した影響と許容条件で定義します。RTOSを採用しただけでは期限を保証できず、割込み、待ち、通信、機器応答も含めます。

3. 学習中ずっと使う共通例

教材では「温度センサーを周期的に読み、ファンの駆動要求を出し、回転を確認する装置」を例にします。温度値の有効性、希望PWM、制御要求の受付、実回転を別の状態として持ちます。車載器なら、車両信号・表示・音声・電源条件も同じ考えで整理できます。

手を動かして確かめる

PCのみ：温度→判断→PWM要求→回転確認の図を描き、各境界で何が分かるかを書いてください。

実機・計測器あり：対象ボードのCPU、RAM、Flash、クロック、入出力、デバッグ端子を資料で特定します。未搭載・不明は分けて記録します。

理解を確かめる

Q1. RTOSを使えば全ての期限を守れますか？

守れるとは限りません。処理・割込み・待ち・機器応答等の上限を含めて設計・検証します。

Q2. PWMを書き込めたらファンは回転していますか？

要求やレジスタ反映と実回転は別です。回転センサー等、必要な観測を確認します。

Q3. SoCという名称だけでLinux搭載が決まりますか？

決まりません。CPU構成・メモリ・製品要件・BSP等と合わせて選びます。

Q4. リアルタイム性を平均処理時間だけで示せますか？

示せません。期限、起点・終点、負荷、最悪時の待ち等を含めて評価します。

CHAPTER 02

02. 信号・回路・周辺機能の基礎

この章で分かること電気的条件とGPIO・クロック・ADC・PWMの意味を読み取れる。
前提知識第1章。電圧・電流・抵抗の基礎。

ソフトウェアが扱う0／1は、実機では電圧と時間の条件で伝わります。配線がつながっていても、論理レベル、入力のしきい値、信号の安定時間、リセット条件が合わなければ正しく動きません。回路図とデータシートを、コードと同じ設計資料として読みます。

1. 信号の条件を確認する

項目意味確認する資料
電源とGND動作電圧の供給と基準電位推奨動作範囲、電源順序、回路図
VIH／VIL・VOH／VOL入力・出力のHigh／Low条件電圧だけでなく電流・温度等の条件も読む
絶対最大定格超えてはならない限界の仕様通常動作の設計目標と混同しない
push-pull／open-drainHigh／Lowを駆動／片側駆動等の方式外付け抵抗、共有線、電圧領域
pull-up／pull-down未駆動時のレベルを定める抵抗抵抗値、漏れ、消費電流、立上り
pin mux一つの端子へ複数機能を割り当てる設定GPIO番号と基板の端子番号は別

例えば3.3 Vと5 Vの信号は、端子の許容条件が確認できなければ直接互換とはしません。MCUのGPIOで負荷を直接駆動できるかも電流・回路次第です。対象の推奨回路、保護、レベル変換等を確認します。ここで示す電圧例は特定ボードへの接続指示ではありません。

2. クロック・リセット・起動条件

クロックはCPUだけでなく、UARTのbaud、タイマー周期、ADCの変換条件にも関係します。周辺クロックの有効化やリセット解除を忘れると、レジスタが読めても機能が準備できていない場合があります。リセット原因を起動時に記録すると、電源投入・watchdog・ソフトウェアリセットを切り分けられます。

3. ADC・DAC・PWM・タイマー

機能何をするか典型的な誤解
ADC電圧等のアナログ入力を数値化分解能と精度は同じではない。基準電圧・誤差・入力条件が必要
DAC数値に応じたアナログ出力を生成負荷を直接駆動できるかは別に確認
PWM周期とHigh時間の比率等で出力を制御duty比が同じでも周波数や負荷で効果が変わる
timer／capture時間測定・周期生成・エッジ時刻取得カウンターの分解能・最大値・wrapを確認

理想的な12 bit ADCで入力範囲を0〜3.3 Vとすると、量子化幅の目安は3.3 / 4096 ≈ 0.806 mVです。コードから電圧への換算式はADCの伝達特性によって確認し、この値を実機の測定精度とは呼びません。PWM周期1 msでHighが250 µsなら、周波数1 kHz、duty 25%です。

4. スイッチのチャタリングと時間条件

機械接点は一度の操作で複数の短い変化を生じる場合があります。最後の変化から一定時間安定した状態を採用する方式、一定周期で連続一致を数える方式等を要件に合わせて選びます。固定の20 msが全スイッチで正しいわけではなく、応答期限と実測を両方確認します。

手を動かして確かめる

PCのみ：PWMの周期・High時間・dutyを相互に計算し、ADCの分解能と精度の違いを説明します。

実機・計測器あり：回路図とpin設定を照合し、許可された測定点で信号の電圧・周期を確認します。プローブの基準と計測器の定格は対象回路に合わせます。

理解を確かめる

Q1. 絶対最大定格の範囲内なら通常動作を保証できますか？

できません。通常の設計は推奨動作条件と各仕様の条件に基づきます。

Q2. GPIO番号と基板の端子番号は同じですか？

別です。端子の割当、pin mux、基板配線を対応付けます。

Q3. 12 bit ADCなら実測精度も12 bitですか？

分解能と精度は別です。基準電圧、各種誤差、入力回路等を確認します。

Q4. PWMのdutyだけで出力の影響を決められますか？

周波数、駆動回路、負荷特性も必要です。要求値と物理結果を分けます。

CHAPTER 03

03. CPU・メモリ・DMAの仕組み

この章で分かることアドレス・配置・cache・DMAの境界を分けて説明できる。
前提知識第1・2章。16進数とbyteの基礎。

CPUは命令を実行し、レジスタやメモリへ値を保持します。組み込み開発では「どのアドレスの何を、どの主体が、いつ読み書きするか」が重要です。通常のRAM、機器レジスタ、DMA用バッファを同じ扱いにしないことが、不具合の予防につながります。

1. 保存領域とメモリマップ

区分役割失敗の例
レジスタCPUの演算・アドレス・状態等割込みや文脈切替の退避条件の誤り
stack関数呼出し、ローカル変数、保存情報等深い呼出し、大きな配列、割込みネストで不足
heap／固定pool実行時のデータ領域確保断片化、枯渇、解放忘れ、使用後解放済み領域へのアクセス
MMU仮想アドレス変換や保護・属性等仮想アドレスを機器のDMAアドレスと同一視
MPU領域ごとのアクセス保護・属性等通常はMMUと同じ仮想アドレス変換機能ではない

2. 幅・順序・配置を読む

エンディアンは複数byteの値をメモリ等へ並べる順序です。通信で受けた2 byteをuint16_tポインタへ単純に変換すると、アラインメント・エンディアン・オブジェクトの扱いの問題が生じ得ます。受信仕様の順序でbyteから値を組み立てる方が意図を示せます。

C11・PCで検証するリトルエンディアンの読取り
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

bool read_u16_le(const uint8_t *data, size_t size, uint16_t *out)
{
    if (data == NULL || out == NULL || size < 2u) return false;
    *out = (uint16_t)((uint16_t)data[0] | ((uint16_t)data[1] << 8));
    return true;
}

dataがsize byteの有効な領域を指すことは呼出し元の契約です。関数内で確認できるのはnullや長さ等であり、任意の不正ポインタを安全に検出できるわけではありません。構造体をそのまま送信する場合もpadding、ABI、版、byte順序を考慮します。

3. cache・DMA・CPUの見える値

DMA（Direct Memory Access）はCPUが各byteを直接コピーし続ける代わりに転送を支える仕組みです。CPU仮想アドレス、CPU物理アドレス、機器が使うDMAアドレスは一致するとは限りません。CPU cacheに古い内容が残る場合や、転送中にCPUが書き換える競合を、所有権とプラットフォームの同期APIで防ぎます。

MMIOではアクセス幅、read-to-clear／write-one-to-clear等の副作用、順序、posted write等も確認します。Linuxドライバではreadl／writel等の適切なアクセサを使い、通常のポインタやmemcpyへ機械的に置き換えません。

手を動かして確かめる

PCのみ：コードへ0x34, 0x12を入力し0x1234になること、長さ0・1やnullを拒否することを確認します。

実機・計測器あり：実機のmapと起動設定を読み、stack上限・RAM範囲・MMIO・DMAバッファの配置を特定します。実アドレスへの任意アクセスは行いません。

理解を確かめる

Q1. DMAへCPUのポインタをそのまま渡せますか？

前提にできません。機器が使うアドレスとCPU側のアドレスを区別し、プラットフォームのAPIを使います。

Q2. volatileを付けるとcache整合性も解決しますか？

解決しません。cache、所有権、機器との同期は別の仕組みです。

Q3. heapを使わなければRAM不足は起きませんか？

起きます。静的領域、各タスクのstack、割込みstack、バッファ等もRAMを使います。

Q4. 受信byte列を構造体へ変換すれば常に正しく読めますか？

保証できません。長さ、アラインメント、padding、エンディアン、ABI等を確認します。

CHAPTER 04

04. C／C++と安全な実装の基礎

この章で分かること型・寿命・volatile・同期の保証範囲を区別できる。
前提知識第3章。Cの関数・配列・ポインタ、C++例にはクラスの基礎。

C／C++の文法だけでなく、処理系が何を保証し、何を保証しないかを理解します。最適化を有効にすると動かなくなるコードは、タイミングだけでなく未定義動作や共有データの問題も疑います。実装依存の挙動は、コンパイラ・オプション・ABI・CPU版と一緒に記録します。

1. 型・演算・ビット操作

対象確認する規則対策
固定幅整数uint32_t等は対応する幅の型がある実装で提供通信・保存形式は幅とbyte順序も明記
整数変換小さな整数型も演算前に整数昇格する符号、幅、比較、明示的な範囲を確認
符号付きoverflowCでは未定義動作になる演算前に上限・下限を検証
符号なし演算対応する幅の範囲で剰余演算になる意図したwrapと値の破損を区別
shift負値や幅以上のshift等に注意符号なし値と検証済みのbit番号を使う
C11・PCで境界値を検証する関数
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

bool checked_add_u32(uint32_t a, uint32_t b, uint32_t *out)
{
    if (out == NULL || b > UINT32_MAX - a) return false;
    *out = a + b;
    return true;
}

bool make_bit_u32(unsigned bit, uint32_t *out)
{
    if (out == NULL || bit >= 32u) return false;
    *out = UINT32_C(1) << bit;
    return true;
}

2. volatileは排他制御ではない

volatileは、処理系の規則に従って対象へのアクセスを扱わせる修飾です。機器レジスタ等で必要になることがありますが、複数スレッドのデータ競合、複数命令の不可分性、一般メモリの並び順、cache整合性を一括して保証しません。「volatile intの++だから安全」という考えは避けます。

目的使う仕組みの候補確認事項
機器レジスタへのアクセスベンダー定義・適切なI/Oアクセサ等アクセス幅、副作用、順序、対象CPU
単一変数の並行更新標準atomicやOS・処理系のatomic APIメモリ順序、lock-free性、ISRで使えるか
複数データの整合mutex、critical section、所有権の分離待てる文脈か、上限時間、マルチコア
割込みとの共有対応する割込み制御やISR向けAPI等割込みマスクだけでは他コアの競合は止まらない

3. 所有権と寿命、C++のRAII

誰が確保し、誰が使い終わり、いつ解放するかを契約にします。非同期APIへローカル配列のアドレスを渡して関数から戻ると、後で寿命切れの領域へアクセスする危険があります。キューへコピーするか、完了まで有効な領域の所有を移すかを決めます。

C++17・PC向け：スコープでmutexを解放する
#include <mutex>

// PC上のC++17例。RTOS・ISRへそのまま持ち込む例ではない。
class BoundedCounter {
    mutable std::mutex mutex_;
    unsigned value_ = 0;
public:
    void increment() {
        std::lock_guard<std::mutex> lock(mutex_);
        if (value_ < 1000u) ++value_;
    }
    unsigned value() const {
        std::lock_guard<std::mutex> lock(mutex_);
        return value_;
    }
};

06. 割込み・周期処理・リアルタイム性

この章で分かること実行文脈と時間の起点・終点を分け、期限とwrapを扱える。
前提知識第2〜5章。

割込みは、外部や周辺回路のイベント等を契機に、現在の実行へ割り込んで処理する仕組みです。イベントを早く受け付ける役割と、全ての作業をその場で終える役割は分けられます。割込みの発生、受理、ハンドラ開始、後段処理、物理応答を別の時刻として測ります。

1. 割込みから後段処理へ

用語意味確認事項

Cortex-MのNVICでは、数値が小さい方が高優先となる例があります。一方、RTOSタスクの優先度表現は別なので、値を同じ意味で流用しません。ポーリングは定期的に状態を確認する方式で、周期・CPU負荷・取りこぼし条件が要件に合えば有効です。

2. カウンターのwrapを扱う

C11・PCでwrap境界を検証する関数
#include <stdint.h>
#include <stdbool.h>

/* 単調に進む32 bit tickの差を使う例。
 * 有効な観測間隔は1周未満。periodは1..2^31-1に制限する。
 * 長期間呼ばれなかった場合の復旧は、呼出し元で別途設計する。 */
bool elapsed_u32(uint32_t now, uint32_t started, uint32_t period)
{
    if (period == 0u || period > UINT32_MAX / 2u) return false;
    return (uint32_t)(now - started) >= period;
}

符号なし減算の剰余を利用するため、startedが最大値付近でnowが小さくなっても短い経過時間を計算できます。ただし1周以上経過した情報はこの値だけでは復元できません。休止中もtickが進むか、復帰後に期限を失効するかは時計と製品の契約で定義します。

3. 応答時間とwatchdog

周期10 msの処理にCPU時間1 msしか使わなくても、ロック待ちや機器応答で期限を超える場合があります。単純な同一単位の例として、検出待ち2 ms、スケジュール待ち1 ms、処理3 ms、出力確認2 msなら合計8 msです。実際には重なる処理、干渉、最悪条件を分析・測定します。

watchdogは一定の条件で応答・更新がなくなったことを検出する仕組みです。独立クロックか、window条件があるか、どの停止を検出できるかを確認します。無条件の周期処理で常にfeedすると、重要タスクが停止しても検出できません。必要な進捗の確認とfeedの条件を結び付けます。

3. 上限付きキューをPCで理解する

C11・PCで検証するFIFOの学習例（並行処理非対応）
#include <stddef.h>
#include <stdbool.h>
#include <stdint.h>

#define BYTE_QUEUE_CAPACITY 4u
typedef struct {
    uint8_t items[BYTE_QUEUE_CAPACITY];
    size_t head, tail, count;
} ByteQueue;

/* 初期化はByteQueue q = {0}; 単一文脈専用。ISR／task共有には使わない。 */
bool byte_queue_push(ByteQueue *q, uint8_t value)
{
    if (q == NULL || q->count >= BYTE_QUEUE_CAPACITY) return false;
    q->items[q->tail] = value;
    q->tail = (q->tail + 1u) % BYTE_QUEUE_CAPACITY;
    ++q->count;
    return true;
}
bool byte_queue_pop(ByteQueue *q, uint8_t *out)
{
    if (q == NULL || out == NULL || q->count == 0u) return false;
    *out = q->items[q->head];
    q->head = (q->head + 1u) % BYTE_QUEUE_CAPACITY;
    --q->count;
    return true;
}

この例はFIFOと容量を学ぶためのコードです。ISRとタスクで同時に呼ぶための同期はありません。実製品ではOSのqueue等を使うか、対象の並行モデルで保証できる方式を設計します。満杯を無視せず、拒否・古い値の破棄・最新値への集約等を用途で決めます。

CRCは定義したbit列の誤り検出を支える仕組みで、攻撃者による改変を防ぐ認証ではありません。多項式だけでなく初期値、bit反転、最終XOR、入力・出力の順序、テストベクタを固定します。キュー上限、部分受信、過大な長さ、切断、再送の上限、タイムアウト後の扱いを検証します。

C11・PCで検証するCRC例（機器操作なし）
#include <stdint.h>
#include <stddef.h>

/* CRC-8/SMBUS: poly=0x07, init=0, refin=false, refout=false, xorout=0。
 * dataはsize byteの有効な領域。size=0の場合は参照しない。
 * 機器プロトコルに適合するかは別途確認する。 */
uint8_t crc8_smbus(const uint8_t *data, size_t size)
{
    uint8_t crc = 0;
    for (size_t i = 0; i < size; ++i) {
        crc = (uint8_t)(crc ^ data[i]);
        for (unsigned bit = 0; bit < 8u; ++bit) {
            unsigned shifted = (unsigned)crc << 1;
            if ((crc & 0x80u) != 0u) shifted ^= 0x07u;
            crc = (uint8_t)shifted;
        }
    }
    return crc;
}

文字列123456789のこのCRC値は0xF4です。実際のSMBus等のフレームへどの範囲を入れるかは別の契約です。テストベクタへの一致だけで通信回路・フレーム全体・全エラーの検出性能を保証しません。

IEC 61508や車載のISO 26262等の適用・版・範囲・要求工程は、対象製品と組織の計画で確認します。この教材は規格本文の代用や適合証明ではありません。規格名を知ること、コーディング規約を使うこと、製品が適合することを区別します。

Q1. 署名したイメージは内容も暗号化されていますか？

署名と暗号化は別です。改変・主体の確認と秘匿の目的を分けます。

要求・設計・interface・試験・版・運用への影響を確認し、関係する証拠を更新します。

Q4. この教材を学べば機能安全規格へ適合したことになりますか？

なりません。規格の適用範囲・工程・製品の証拠等を別に評価する必要があります。
